## 2. Win32 収集ルール（唯一の規則）と今回の検証

> **sdk-api のページは「Windows CE 自身のドキュメントがその API 名を
> 扱っている」ときだけ収集する。それ以外は収集しない。**

前回の見直しで、この規則に合わない 11,819 ページ（デスクトップ専用）を削除し、
`data/win32-exclude.tsv` に「名前が偶然一致しただけ」の例外を記録しました。
今回のラウンドでは、この規則を**逆方向から**検証しました。

* `tools/build-win32-coverage.py` は「CE のページが Win32 の共通ヘッダ
  （`Winbase.h` / `Winuser.h` / `Windows.h` 等）を挙げているのに、Win32 側の
  ページが無い名前」を列挙します → `data/reports/win32-coverage.tsv`（992 件）。
* 内訳: **782 件は WM_* / CB_* / TVN_* などのメッセージ・通知・マクロ定数**
  で、sdk-api は定数ごとのページを持たない種類のものです（= 収集漏れではない）。
  残る **210 件は CE 固有 API**（`Ce*` RAPI 群、`CommandBar_*` など CE 独自の
  commctrl、`CEBLOB` などの構造体）や、Win32 側で廃止された API
  （`GetStringType`、`Random`、`SetDaylightTime`）でした。
  **「Win32 側にページがあるのに取り忘れている」名前は 0 件**でした。
* 名前の綴り違いもここで解消しています。Win32 のリファレンスは綴りごとに
  ページを持ち（`CreateSemaphoreW`）、CE のページは基底名
  （`CreateSemaphore`）を扱うため、以前は別エンティティになっていました。
  ページ自身の「Unicode and ANSI」記述を根拠に **893 件**を基底名へ結合し、
  うち 447 件が Win32 ページを基底名に結びつけました（推測はしていません。
  記述が無い 62 件はそのまま別エンティティです）。
* Win32 側で文書化されていると分かった名前は 5,451 件（うち 4,293 件は
  CE のページも持つ = 共通部分）。共通部分の関係は各エンティティの
  `relations`（`layer`, `unicode-ansi*`）と `data/reports/win32-shared.tsv`
  の両方から辿れます。

## 6. 知識基盤 `knowledge/`（追跡可能性と今回の精度向上）

このリポジトリの目的は「完成した include/def そのもの」ではなく、**それらを
生成するための、機械可読で追跡可能な情報の集積**です。`tools/build-kb.py` が
corpus の全 121,039 ページを解析して `knowledge/` を書き出します
（再実行 1 分強、手で編集しない）。

```
knowledge/
├── kb/entities.jsonl.gz             API 名ごとの知識（24,442 件、関係と用途つき）
├── kb/declarations.jsonl.gz         C/C++ の宣言・構造体定義（78,442 件、逐語）
├── kb/declarations-dotnet.jsonl.gz  .NET 層のシグネチャ（31,326 件、分離）
├── kb/requirements.jsonl.gz         Header / Library / DLL / モジュール / OS 版（156,514 件）
├── kb/constraints.jsonl.gz          CE 固有の制約・拡張の文（3,239 件、原文引用）
├── kb/headers.tsv / libraries.tsv / dlls.tsv /               集計ビュー
│   modules.tsv / sets.tsv
├── reports/coverage*.tsv           ツリー別・エンティティ別の被覆状況
├── reports/gaps.tsv                未収集の作業リスト（14,706 件）
├── reports/filtered-values.tsv     「Developer Implemented」等、ファイル名を
│                                   持たない Header/Library 値（捏造しないため
│                                   マップに入れず、記録だけ残す）
└── schema/*.json                   4 種類のレコードの JSON Schema
```

**今回の精度向上:**

* **呼び出し規約（`calling_convention`）** を宣言レコードに追加。宣言本文に
  `WINAPI` / `CALLBACK` / `_stdcall` / `_cdecl` / `_fastcall` / `extern "C"` が
  現れたときだけ値を入れます（未記載は `null`。74,291 件が未記載、
  `winapi` 3,169 / `stdcall` 639 / `cdecl` 313 / `extern-c` 29 / `fastcall` 1）。
* **名前の綴り統合**（§2）: `variants_of` / `variants` /
  `win32_pages_from_variants` を追加し、関係 `unicode-ansi-variant` を記録。
* **要求値の衛生**: `Library: Developer Implemented` のような「ファイル名を
  持たない値」は、原文のレコードを残したまま派生キーを空にして
  ヘッダ/ライブラリ/モジュールの対応表から外しました
  （`knowledge/reports/filtered-values.tsv` に一覧）。
* **検証ツール `tools/check-kb.py`**: 必須フィールド・ID 形式・出典ページの
  存在・参照先 ID の解決・`present` の整合を検証し、KB の重複レコードも
  検出します（現在は `knowledge OK`）。GitHub Actions の 5 ワークフローにも
  組み込みました。
* **重複レコードの不具合を修正**: 同じページが同じブロックを 2 回書いていた
  場合に 1 レコードが二重に出ていました（`getstringtypeex` の幽霊関係として
  発覚）。4 種類すべての書き出しで ID 単位に重複を除いています。

**追跡可能性（ご指示の 4 点）をどう持たせているか**:

| ご指示 | 実装（現状） |
|---|---|
| どの資料に基づくか | 全レコードに `source`（corpus 相対パス・page_id・セット・タイトル・layer）。宣言・要求・制約は**必ず**出典を持ちます |
| どのバージョン・世代か | エンティティの `ce_sets`（例 `learn/windows-embedded-ce-6.0`）と `requirements` の `os_versions`、`kb/sets.tsv` のセット別集計 |
| 他の定義・仕様との関係 | `relations` に明示: `unicode-ansi` / `unicode-ansi-base` / `unicode-ansi-variant`（ページ自身の "CreateFileW (Unicode) and CreateFileA (ANSI)" 記述に基づく）、`interface-method`（`Interface::Method` = vtable の持ち主）、`layer`（CE と Win32 の両方が文書化）。各関係は対象名・対象の有無（`present`）・出典ページ・引用文つき |
| include/def 生成にどう使えるか | `generation_use`（`include-declaration` / `type-definition` / `link-library` / `def-export` / `abi-layout` / `unicode-mapping` / `version-scope` / `ce-restriction`）＋ `headers.tsv`（include 対応）・`libraries.tsv`/`dlls.tsv`/`modules.tsv`（リンク・モジュール対応）・`gaps.tsv`（不足分の作業リスト） |

方針として守っていること:

* **捏造しない。** 出典の無い値は入れません。CE に無い API を補完したり、
  Win32 の値を CE に流用したりはしません。
* **C のテキストを勝手に直さない。** 宣言は逐語。`spacing: "collapsed"` は
  「そのページ自身が空白を失っている」ことを示すフラグで、本文は修復しません。
* 派生値（`kind`、`doc_role`、`spacing`、要求の `field`/`key`、
  `calling_convention`、`variants_of`）は Schema に「DERIVED」と明記し、
  元のラベル・原文を併記します。

## 7. 生成の試作（include/def の材料を実際に出す）

`tools/gen-include-def.py` は知識基盤の最初の消費者です。1 つの CE バージョン
（例: `learn/windows-ce-5.0`）を指定して、次を書き出します（出力先は
git 管理外の `build/generated/wince50` など）。

```bash
python3 tools/gen-include-def.py --list
python3 tools/gen-include-def.py --set learn/windows-ce-5.0 \
    --out build/generated/wince50
python3 tools/gen-include-def.py --set chm/windows-ce-3.0 \
    --out build/generated/wince30 --no-borrow
```

CE 5.0 を対象にした今回の結果:

| 出力 | 内容 |
|---|---|
| `include/<Header>.h.fragment` 592 ファイル | そのヘッダの宣言を**逐語で**。各ブロックに出典ページ・ライブラリ・種類をコメントで付記。include ガードや並び順は生成側の仕事（断片であることを明記） |
| `link/<module>.def` 184 ファイル | モジュール別の EXPORTS 作業リスト（関数・コールバックのみ。構造体・typedef・C++ メソッドは出しません）。`coredll.lib` と `coredll.dll` のような綴りは 1 モジュールにまとめ、ファイル先頭に「元の綴り」を列挙 |
| `manifest.tsv` | エンティティ ↔ ヘッダファイル/モジュール ↔ 宣言 ID ↔ 出典ページ ↔ 借用の有無 ↔ バージョン |
| `report.md` | 生成できた数と、**できなかった理由の内訳** |

* 宣言 15,503 件（うち他セットから借用 927 件。借用はマニフェストと
  コメントに記録）、エクスポート行 4,382 件。
* 出力できなかった内訳: 宣言が無い 1,826 / ヘッダの記載が無い 1,168。
  これは `knowledge/reports/gaps.tsv` と同じ作業リストです。
* `.def` は**作業リスト**であり完成品ではありません。ドキュメントには
  装飾名（`_Name@N`）・序数・エクスポートテーブルが無いため、ファイル先頭に
  その旨を明記し、SDK と突き合わせる前提にしています（捏造しない）。
* 生成物はリポジトリに入れません。`build/` は `.gitignore` 済みで、
  再生成は 3 秒程度です。

3. **収集の優先順位**: 残る収集候補は (a) Platform Builder の製品ドキュメント
   （CE .NET 4.x / CE 5.0 CD1 の CHM 群）、(b) `missing-pages.tsv` の残り 1 件、
