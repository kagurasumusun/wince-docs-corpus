記録です。英語の正本は [`COLLECTION-POLICY.md`](COLLECTION-POLICY.md)、
リポジトリ直下の `README.md`、`knowledge/README.md`。ここはその日本語での
要約と、判断の根拠・残っている宿題です。

## 2. Win32 収集ルール（唯一の規則）

> **sdk-api のページは「Windows CE 自身のドキュメントがその API 名を
> 扱っている」ときだけ収集する。それ以外は収集しない。**

* 名前の判定元は `tools/ce_api_names.py` 1 ファイル。根拠は
  `data/reports/ce-api-names.tsv`（CE が扱う名前 **31,922 件**、各名前の
  CE 側ページ ID・収録セット付き）。
* `A`/`W` は基底名で判定（CE が `CreateFile` を扱うので `CreateFileA`/`W` も採る）。
* 例外は `data/win32-exclude.tsv` に**理由付きで 9 件**だけ（`run`、`address`、
  モジュール 7 件: `roapi`, `devicetopology`, `cloneviewhelper`, `d2d1helper`,
  `d2d1_1helper`, `exposeenums2managed`, `icontact`, `mstask`）。
* 証拠は 2 方向ともファイル化:
  * `data/reports/win32-imported.tsv` — 収録 5,279 ページそれぞれの CE 側根拠
  * `data/reports/win32-shared.tsv` — 共有名 5,068 件の CE 側 ↔ Win32 側対応
  * `data/reports/win32-coverage.tsv`（今回追加）— **逆方向の見直し**。
    「CE 側のページが Win32 のヘッダ（Winbase.h 等）を挙げているのに
    `corpus/win32/` にページが無い名前」1,226 件の一覧。大半はコンパイラ
    イントリンシック・CE 固有拡張・sdk-api にページが無い名前で、**除外しすぎ
    ではないことの確認用**。うち 16 件（`_InterlockedIncrement` ↔
    `InterlockedIncrement` 等）は綴り違いの可能性を候補として表示。

## 3. .NET 系の分離（ご指示「.net は分離」の実施結果）

`corpus/learn/` に混ざっていた .NET 系 10,657 ページを **`corpus/dotnet/`** に
移動しました（削除ではありません）。

| セット | ページ数 | 内容 |
|---|---|---|
| `dotnet/pos-for-net/` | 5,793 | POS for .NET（`Microsoft.PointOfService`） |
| `dotnet/dotnet-micro-framework/` | 4,012 | .NET Micro Framework（`Microsoft.SPOT.*` 等） |
| `dotnet/dotnet-compact-framework/` | 852 | .NET Compact Framework（`System.*`） |

* リネームは `git mv` で履歴を保っています。`tools/harvest.py` に
  `DOTNET_DIR`/`DOTNET_SETS` を追加し、**今後の収集でも .NET 系は自動的に
  `corpus/dotnet/` に入ります**。
* `tools/check-policy.py` / `tools/build-index*.py` / ナレッジ基盤も 9 ツリー
  （CE 6 + .NET 1 + Win32 1 + 後述 site 1）として扱います。
* 分離の理由は `corpus/dotnet/README.md` に明記: 管理コードのクラス・
  名前空間の文書であり、ヘッダ宣言やエクスポートを持たない = include/def の
  材料にならない。加えて `Font`/`Image`/`Timer` のような名前が Win32 の
  無関係な API と衝突するため、従来から Win32 判定からは除外していました。
* 知識基盤でも同じ分離: .NET ページのレコードは `layer: "dotnet"` を持ち、
  そのシグネチャブロック（C#/VB/C++/JScript）は
  `knowledge/kb/declarations-dotnet.jsonl.gz` に**別ファイル**で出力します
  （C の宣言ファイル `kb/declarations.jsonl.gz` には混ぜません）。
  .NET ツリーからエンティティは 0 件（＝ヘッダ宣言を述べるページが無い、
  という正直な結果）。

## 4. 重複の解消（672 グループ → 0）

前回「メディア固有の重複なので残す」と報告した 672 グループを、**1 ページを
残して解消**しました（削除した側は `data/index/aliases.tsv` に 1 行ずつ記録、
計 673 行 = メディア由来 672 + `site/` 取り込み時に混ざった FrontPage の
一時コピー 1）。

注: このとき**別名テーブルがツール再実行で上書きされる不具合**に気づき、
修復しました。記録は `duplicates.tsv`（git 履歴）とディスク上の残存ページから
再構成し、ツール側は「既存の別名を消さない（削除ページが復活したときだけ
行を落とす）」方式に変更済みです。

* 内訳（前回調査のとおり）: 640 = CE 2.12 SDK リファレンスが DevCon '99 CD と
  `datadungeon`（MSDN Library 2000-04 CD）の両方に収録 / 30 = CE 5.0
  コンポーネント CHM の `wcemouse5` と `wcestylus5` の重複 / 2 = CE 1.0 の
  1 冊が同じ CD に 2 回収録。
* 残す側の優先順位（権威の高い資料を残す）:
  `learn` > `dotnet` > `chm` > `mvb` > `wcedevcon-99` > `techshelps` > `kb` >
  `windows-mobile-6.5` > `2010-05` > `datadungeon`。
  例: 640 グループは `wcedevcon-99` を残し `datadungeon` 側を削除。
* **取り込みツール側にも再発防止**を入れました: `tools/alias_index.py` を
  `harvest.py` / `crawl-mirror.py` / `extract-chm.py` / `import-media.py` が
  参照し、**削除済みページが再び入ってきたら書き込まずスキップ**します
  （削除されたページ ID は「別名」として解決可能）。
* `corpus/msdn-library/2010-05/`（161 ページ）は Learn と同内容ですが、
  **別キャプチャ（2010-05 の MSDN レンダリング）**なので残しています。方針として
  不要と判断されれば同じ手順で削除できます。

## 6. 知識基盤 `knowledge/`（今回の追加）

このリポジトリの目的は「完成した include/def そのもの」ではなく、**それらを
生成するための、機械可読で追跡可能な情報の集積**です。`tools/build-kb.py` が
corpus の全 121,058 ページを解析して `knowledge/` を書き出します
（再実行 1 分、手で編集しない）。

```
knowledge/
├── kb/entities.jsonl.gz             API 名ごとの知識（24,442 件、関係と用途つき）
├── kb/declarations.jsonl.gz         C/C++ の宣言・構造体定義（78,518 件、逐語）
├── kb/declarations-dotnet.jsonl.gz  .NET 層のシグネチャ（31,827 件、分離）
├── kb/requirements.jsonl.gz         Header / Library / DLL / モジュール / OS 版の要求（156,548 件）
├── kb/constraints.jsonl.gz          CE 固有の制約・拡張の文（3,289 件、原文引用）
├── kb/headers.tsv / libraries.tsv / dlls.tsv /               集計ビュー
│   modules.tsv / sets.tsv
├── reports/coverage*.tsv           ツリー別・エンティティ別の被覆状況
├── reports/gaps.tsv                未収集の作業リスト（14,042 件）
└── schema/*.json                   4 種類のレコードの JSON Schema
```

**追跡可能性（ご指示の 4 点）をどう持たせているか**:

| ご指示 | 実装（現状） |
|---|---|
| どの資料に基づくか | 全レコードに `source`（corpus 相対パス・page_id・セット・タイトル・layer）。宣言・要求・制約は**必ず**出典を持ちます |
| どのバージョン・世代か | エンティティの `ce_sets`（例 `learn/windows-embedded-ce-6.0`）と `requirements` の `os_versions`（"Windows CE versions: 5.0 and later" 等）、`kb/sets.tsv` のセット別集計 |
| 他の定義・仕様との関係 | `relations` に明示: `unicode-ansi`（ページ自身の "CreateFileW (Unicode) and CreateFileA (ANSI)" 記述に基づく A/W 対応）、`unicode-ansi-base`（その記述から導いた基底名との対応）、`interface-method`（`Interface::Method` = vtable の持ち主）、`layer`（CE と Win32 の両方が文書化）。各関係は対象名・対象の有無（`present`）・出典ページ・引用文つき。加えて `win32_pages`/`ce_pages` と `data/reports/win32-shared.tsv` |
| include/def 生成にどう使えるか | 各エンティティの `generation_use`（`include-declaration` / `type-definition` / `link-library` / `def-export` / `abi-layout` / `unicode-mapping` / `version-scope` / `ce-restriction`）に、レコードがどの工程に使えるかを規則ベースで明示。`headers.tsv`（include 対応）、`libraries.tsv`/`dlls.tsv`/`modules.tsv`（リンク・モジュール対応）、`gaps.tsv`（不足分の作業リスト） |

方針として守っていること:

* **捏造しない。** 出典の無い値は入れません。CE に無い API を補完したり、
  Win32 の値を CE に流用したりはしません。
* **C のテキストを勝手に直さない。** 宣言は逐語。`spacing: "collapsed"` は
  「そのページ自身が空白を失っている」ことを示すフラグで、本文は修復しません
  （他ソースの同名宣言を使う判断は生成側ができます）。
* 派生値（`kind`、`doc_role`、`spacing`、要求の `field`/`key`、宣言の
  `language`）は Schema に「DERIVED」と明記し、元のラベル・原文を併記します。

## 7. ご確認いただきたい点

1. **配置**（資料・知識・生成物・生成元の区別）:
   現在は `sources/`（資料＝媒体・上流スナップショット）/ `corpus/`
   （資料＝ページ）/ `knowledge/`（知識）/ `data/`・`queues/`・`tools/`・
   `docs/`（収集の作業データと生成元）という分け方です。
   **生成物**（将来の include/def 出力）は、リポジトリに入れず
   git 管理外の `build/` などに出す想定です。
   この分け方でよいか、`knowledge/` を `corpus/` の下に置くべきか等、
   ご指示ください。
2. **知識レコードの単位** — いまは「API 名（エンティティ）」を単位に
   宣言・要求・制約をぶら下げています。資料単位（ページ）／ヘッダ単位の
   ビューも必要か、ご指示ください。
3. **残りの宿題**（次回以降で実施）:
   * ~~関係・用途の明示（`relations` / `generation_use`）~~ → 実施済み（上記）
   * ~~カタログ由来のノイズ（`__COMMONPUBROOT` 等のビルド変数名）の除去~~
     → 実施済み: 削除ではなく `noise: "build-variable"` フラグで識別
     （`reports/gaps.tsv` からは除外、レコードは原文のまま残す）
   * Platform Builder 系 CHM の棚卸しと収集
   * 生成側（include/def 出力）の試作 — これは別リポジトリ/生成物側の話に
     なります
