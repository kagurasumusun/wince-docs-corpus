# 2026-10 見直しレポート（日本語）

`wince-docs-corpus` の収集方針を見直し、余分な収集を削除し、二度と同じことが
起きないようにした記録です。英語の正本は
[`COLLECTION-POLICY.md`](COLLECTION-POLICY.md)（収集方針）と
リポジトリ直下の `README.md`。ここはその日本語での要約と、判断の根拠です。

## 1. 結論

* 集めていた「余分」の原因は 2 つでした。どちらも**収集ツールが広すぎる単位で
  取っていた**ことによるものです。

  1. **Win32 を「モジュール単位」で丸ごと取得**していた
     （`tools/fetch-upstream.py` の `--scope modules` が既定）。
     結果、`corpus/win32/` の 20,452 ページのうち **11,819 ページが
     デスクトップ専用の sdk-api ページ**（Shell、DirectX、WMI、WinRT、
     Windows Media、メディアファウンデーション等）、さらに
     **デスクトップ向け Win32 プログラミングガイド 3,357 ページ**
     （トランザクション NTFS、変更ジャーナル等）を含んでいました。
  2. **古いメディア（DevCon '99 会議 CD）を丸ごと取り込み**、スポンサー広告・
     サンプルツリー・FrontPage メタデータなど **1,051 ページ**を拾っていました。

* 現在のルールは 1 つだけです。

  > **sdk-api のページは「Windows CE 自身のドキュメントがその API 名を
  > 扱っている」ときだけ収集する。それ以外は収集しない。**

  モジュールの「文脈（context ring）」は廃止しました。`A`/`W` 版は CE が基底名を
  扱っていれば一緒に採ります（CE が `CreateFile` を扱うので `CreateFileA` /
  `CreateFileW` を採る）。

* 現在の枚数: **121,686 ページ = CE 116,407 + Win32 共通部分 5,279**。
  今回の見直しで **16,228 ファイル（68 MB）を削除**しました。

* 収集するのは**ドキュメントだけ**です。ソースコード・ヘッダ・サンプル・
  バイナリは `corpus/` に 0 件で、混入すれば `tools/check-corpus.py`
  （`source_files`）と `tools/check-policy.py`（`source or binary`）が失敗します。

* 「証拠」を丸ごとファイル化しました。判断はすべて再確認できます。

  | ファイル | 内容 |
  |---|---|
  | `data/reports/ce-api-names.tsv` | CE が扱う API 名 **31,923 件**。各名前について CE 側のページ ID と収録セット（根拠） |
  | `data/reports/win32-imported.tsv` | 収録した Win32 **5,279 ページ**それぞれの CE 側根拠（ページ ID 付き） |
  | `data/reports/win32-shared.tsv` | 共有名 **5,068 件** → CE 側ページ・Win32 側ページの対応 |
  | `data/win32-exclude.tsv` | 例外的に除外する **2 名 + 7 モジュール**（理由付き。後述） |
  | `data/reports/duplicates.tsv` | 重複グループ 672（すべてメディア由来。後述） |

* 再発防止として `tools/check-policy.py` を追加し、**すべての収集ワークフロー
  の最後に実行**するようにしました（方針違反のページが入ると CI が落ちます）。

## 2. 現在の Win32 収集ルール（唯一の規則）

収録条件（`tools/ce_api_names.py` が唯一の判定元）:

1. **名前の一致**。CE 側の正本カタログ（`data/catalogs/*.tsv` = CE 3.0 / 5.0 /
   .NET 4.x / Embedded CE 6.0 の製品ドキュメントのページタイトル）と、
   カタログの無い CE セット（CE 1.0/2.0 Books Online、MSDN Library の CE セット、
   CE 2.12 SDK（DevCon '99）、2010-05 キャプチャ、Windows Mobile 6.5、KB、
   CE 4.2/5.0 CHM）から索引経由で抽出した名前。
   `.NET` のオブジェクトドキュメント（`dotnet-*`、`pos-for-net`、`VBCE`）は
   **意図的に除外**しています（`Font` や `Image` のようなクラス名が Win32 の
   無関係なページと衝突するため）。
2. `A`/`W` は基底名で判定。
3. `data/win32-exclude.tsv` の例外を除去。

除外した例外（全 9 件、理由付きで同ファイルに記載）:

| 種別 | 対象 | 理由（要点） |
|---|---|---|
| 名前 | `run` | CE の `Run (Windows Media Player)` はプリンタドライバの `RUN` 構造体ではない |
| 名前 | `address` | CE 3.0 DDK の `Address` はディスプレイドライバのエントリポイントで、dbghelp の `ADDRESS` 構造体ではない |
| モジュール | `roapi` | Windows Runtime（CE に存在しない） |
| モジュール | `devicetopology` | Core Audio のデバイストポロジ（Vista 以降） |
| モジュール | `cloneviewhelper` | ディスプレイ複製ヘルパ（Windows 7 以降） |
| モジュール | `d2d1helper` / `d2d1_1helper` | Direct2D ヘルパ |
| モジュール | `exposeenums2managed` | シムデータベースの `TAG` マクロ（CE の Mobile Channels の `TAG` とは別物） |
| モジュール | `icontact` | Windows Contacts（`contacts.h`）。CE 側の同名 `IContact` は Pocket Outlook の連絡先オブジェクト |
| モジュール | `mstask` | デスクトップのタスクスケジューラ。CE 側の同名 `ITask` は Pocket Outlook のタスク |

### 検証（「名前が合っているだけ」で採っていないか）

* 収録した 5,279 ページのうち **5,131 ページ**は、**corpus 内に同名の CE ページ
  が実在**します（例: `SOCKADDR_BTH (Windows CE 5.0)`、`in6_addr (Windows CE 5.0)`）。
  証拠は `win32-imported.tsv` にページ ID で入っています。
* 残り **148 ページ**（CE 側がカタログ項目や SDK のアンカーページ）は
  **1 件ずつ CE 側のページを開いて確認**しました。148 件は
  `IUnknown`、`IMalloc`、`DMO` 系、UPnP、DSROLE 等の同名 CE ページで、
  CE 側ページのタイトルに API 名が含まれることも機械的に確認済みです
  （不一致 0 件）。この確認の過程で誤り 1 件（`address` = CE 3.0 DDK の
  ディスプレイドライバ `Address` と dbghelp の `ADDRESS` 構造体）を発見し、
  除外に追加しました。
  → この作業で追加削除したのは 4 ページ（`icontact` 2、`mstask` 1、
  `exposeenums2managed` 1）＋ `address` 1 ページです。
* **ツリーとルールの機械照合**: 固定コミットの tarball から同じ抽出を再実行し、
  生成されるはずのパス集合と `corpus/win32/api/` の実ファイル集合が
  **完全一致**することを確認しました（追加 0・欠落 0）。
* CE 側のどのセットも「デスクトップ専用 API を CE の名前で採っていないか」を
  逆方向からも確認しました（`learn/` は全 68,703 ページが
  `previous-versions/windows/embedded` 名前空間、他製品の混入は
  Commerce Server の 1 ページのみ → 削除）。

### 「共有部分」として残したもの（除外しすぎていないか）

GDI+、TAPI/TSPI、UPnP、WSD、P2P/PNRP、Smart Card、LDAP、WinInet、ICM、
DirectShow / Windows Media、Bluetooth、RDP の仮想チャネル、ジェスチャ等は、
**Windows CE 自身がそれらの API をドキュメントしている**ため残しています
（CE 5.0 / CE 6.0 のページ ID 付きで `win32-imported.tsv` に記録）。
迷ったものは「CE 側のページが実在するか」で判断し、判断理由をファイルに残しました。

## 3. ソースコードを集めていないこと

* `corpus/` に `.c` / `.h` / `.cpp` / `.cs` / `.rc` 等はありません
  （`check-corpus.py --report`: `source_files = 0`）。
* メディア（CD イメージ）は `corpus/` へ直接展開しません。
  `tools/import-media.py` が中身を分類し、製品のドキュメントだけを取り込み、
  サンプル・ヘッダ・ツールチェーン・OS イメージは「数えてスキップ」します。
  取り込む側の条件は `queues/media.tsv` のメディアごとの除外正規表現です。
* コードが本文に載っている**ドキュメントページ**（KB 記事、CHM のサンプル章など
  約 130 ページ）は残しています。これは「資料」そのものなので対象内です。

## 4. 重複 672 グループについて（調査結果）

`data/reports/duplicates.tsv` の 672 グループは、**メディア固有の重複**で、
取り込みミスではありません。

* 640 グループ: CE 2.12 SDK リファレンスが DevCon '99 CD と
  `datadungeon`（MSDN Library 2000-04 CD）の両方に収録されている（同一内容）。
* 30 グループ: CE 5.0 コンポーネント CHM の `wcemouse5` と `wcestylus5` が
  マウス／スタイラスのページを共有している。
* 2 グループ: CE 1.0 の 1 冊が同じ CD に 2 回収録されている。

同じ理由で `corpus/msdn-library/2010-05/`（161 ページ）は Learn の同ページと
重複しますが、これは**別のキャプチャ（2010-05 の MSDN レンダリング）**なので
意図的に残しています。不要と判断されれば削除できます。

## 5. ご判断いただきたい点: .NET 系 10,657 ページ

以下は Windows CE / Windows Embedded の名前空間にある製品ドキュメントですが、
**Win32 API リファレンスではありません**（.NET のクラスライブラリ文書）。

| セット | ページ数 | 内容 |
|---|---|---|
| `corpus/learn/pos-for-net/` | 5,793 | POS for .NET（.NET 向け小売端末 API） |
| `corpus/learn/dotnet-micro-framework/` | 4,012 | .NET Micro Framework |
| `corpus/learn/dotnet-compact-framework/` | 852 | .NET Compact Framework |

選択肢:

* **(a) 残す**（現状）— CE プラットフォーム向け製品のドキュメントであり、
  「Windows Embedded の資料」としては対象内。
* **(b) 削除する** — 「Win32 共通部分」ではないので、厳密な方針では余分。
* **(c) 別ツリーへ分離**（例 `corpus/dotnet/`）— CE 本体の資料と .NET 系を
  明確に分ける。

私の推奨は **(c) または (a)**（判定は方針次第でどちらも妥当）です。
削除する場合は (b) を選んでください、同じ手順で実施します。
