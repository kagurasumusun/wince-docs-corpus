# 2026-10 見直しレポート（日本語）

`wince-docs-corpus` の収集方針を見直し、余分な収集を削除し、重複を解消し、
**WinCE 向け include/def を生成するための知識基盤**（`knowledge/`）を整え、
その知識基盤から include/def の材料を生成する試作まで通した記録です。

**このリポジトリの前提（最初に確認しておくこと）**

> **Windows CE は完全な Win32 ではありません。**
> WinCE が持つのは **「WinCE 固有の部分」＋「Win32 と共通の部分」** であり、
> Win32 全体を実装したものではありません。したがって収集・生成のどちらでも、
> 「CE が名前を扱っているか」を境界として扱います。

英語の正本は [`COLLECTION-POLICY.md`](COLLECTION-POLICY.md)、リポジトリ直下の
`README.md`、`knowledge/README.md`。ここはその日本語での要約と、判断の根拠・
残っている宿題です。

## 2. 境界: WinCE は Win32 の全部ではない

### 2.1 収集の規則（唯一の規則）

> **sdk-api のページは「Windows CE 自身のドキュメントがその API 名を
> 扱っている」ときだけ収集する。それ以外は収集しない。**

前回の見直しでこの規則に合わない 11,819 ページを削除し、
`data/win32-exclude.tsv` に「名前が偶然一致しただけ」の例外を記録しました。
今回、この規則を**逆方向から実測**しました（`data/reports/win32-coverage.tsv`）。

* CE のページが共通ヘッダ（`Winbase.h` / `Winuser.h` など）を挙げているのに
  Win32 側にページが無い名前は **960 件**。うち **768 件は WM_* / CB_* / TVN_* の
  ようなメッセージ・通知・マクロ定数**で、sdk-api は定数ごとのページを持たない
  種類のものです。残りは CE 固有 API（`Ce*` RAPI、`CommandBar_*` など）と、
  Win32 側で廃止された API（`GetStringType`、`Random`）。
  → **「Win32 側にページがあるのに取り忘れている」名前は 0 件**。

### 2.2 知識基盤での境界（今回追加）

各エンティティに **`surface`**（`knowledge/reports/surface.tsv` にも同内容）を
持たせました。

| `surface` | 件数 | 意味 |
|---|---:|---|
| `ce-only` | 18,931 | Windows CE だけが文書化している名前（CE 固有部分） |
| `shared` | 4,353 | CE と Win32 リファレンスの**両方**が文書化している名前（共通部分） |
| `win32-spelling` | 1,155 | CE が文書化する名前の A/W 綴りとして収集した Win32 ページ（`variants_of` つき） |
| `catalog-only` | 3 | 公式 CE カタログにだけ載る名前。手元にあるのは Win32 ページだけ＝**収集リード**（`AVIMAINHEADER`/`MESSAGE`/`SECTION`） |
| `win32-only` | 0 | CE の名前と結びつかない Win32 ページ。**0 件**（取り込んだ Win32 ページはすべて CE 側の名前が根拠） |

* A/W 綴りの結合（第 3 ラウンドの 893 件 → 今回 1,155 件）は、**根拠の種類**を
  `variants_of.basis` に明記しました:
  `page-statement`（ページ自身の "X (Unicode) and Y (ANSI)" 記述、1,057 件）と
  `import-rule`（`data/reports/win32-shared.tsv` が「その CE 名の綴りとして取り込んだ」
  と記録している、98 件）。どちらも無い綴りは結合しません（名前だけで推測しない）。
* `catalog-only` の 3 件は「CE のカタログが名前を挙げている」以上、CE の資料が
  どこかにあるはずだ、という作業リストです（Win32 の定義を CE の定義として
  流用しないため、`surface` で区別しています）。

### 2.3 生成側での境界（今回変更）

`tools/gen-include-def.py` は、対象 CE バージョンの **`ce_sets` に載っている
名前だけ**を出力します。宣言の優先順位も境界に沿って決めます。

1. 対象 CE セット自身のページが印刷した宣言（最優先）
2. 別の CE セットのページが印刷した宣言（借用として明示）
3. **Win32 リファレンスのページの宣言** — CE のページが宣言を持たないときだけ、
   そして**必ず「Win32 参照（デスクトップ Windows の文書）なので CE SDK と
   突き合わせること」と印を付けて**出力（フラグメントのコメント・`manifest.tsv`
   の `borrowed_from` 列・`.def` の行末コメント・`report.md`）

CE 5.0 を対象にした今回の結果では、**Win32 からの流用は 0 件**（出力 15,524 宣言の
うち、CE セット内 14,597 + 別 CE セットからの借用 927）でした。CE 1.0 SDK のような
古いセットでは 1 件だけ Win32 流用が発生し、印つきで出ることを確認しています。
`--include-win32` は「CE の根拠がある名前の Win32 ページも材料に加える」という
スイッチで、**CE の根拠が無い Win32 専用名は決して出力しません**。

`tools/build-kb.py` が corpus の全 121,039 ページを解析して `knowledge/` を

│                                     kinds / layers / surface / ce_sets /
│                                     headers / libraries / dlls / modules /
│                                     relations / variants / generation_use
├── kb/declarations.jsonl.gz         C/C++ の宣言・構造体定義（78,442 件、逐語）
├── kb/declarations-dotnet.jsonl.gz  .NET 層のシグネチャ（31,326 件、分離）
├── kb/requirements.jsonl.gz         要求（Header/Library/DLL/モジュール/OS 版、156,514 件）

**精度のために今回追加・修正したもの:**

* **`surface`**（§2.2）と **`variants_of.basis`**（結合の根拠の種類）。
* **宣言の `calling_convention`**（WINAPI / CALLBACK / _stdcall / _cdecl /
  _fastcall / extern "C"。未記載は null。推測しない）。
* **重複レコードの不具合修正**（同じページが同じブロックを 2 回書いていた場合に
  1 レコードが二重に出ていた。4 種類すべての書き出しで ID 単位に重複を除去）。
* **要求値の衛生**: `Library: Developer Implemented` のようなファイル名を持たない
  値は、原文レコードを残したまま派生キーを空にし、対応表から外す
  （`reports/filtered-values.tsv`）。
* **検証ツール `tools/check-kb.py`**: 必須フィールド・ID 形式・出典ページの存在・
  参照先 ID の解決・`present` と `surface` の整合・重複レコードを検証。
  GitHub Actions の 5 ワークフローに組み込み済み。

**追跡可能性（ご指示の 4 点）:**

| ご指示 | 実装 |
|---|---|
| どの資料に基づくか | 全レコードに `source`（corpus 相対パス・page_id・セット・タイトル・layer）。宣言・要求・制約は**必ず**出典を持ちます |
| どのバージョン・世代か | エンティティの `ce_sets`（例 `learn/windows-embedded-ce-6.0`）、要求の `os_versions`、`kb/sets.tsv` のセット別集計 |
| 他の定義・仕様との関係 | `relations`: `unicode-ansi` / `unicode-ansi-base` / `unicode-ansi-variant`（ページ自身の記述に基づく）、`interface-method`（`Interface::Method` = vtable の持ち主）、`layer`（CE と Win32 の両方が文書化）。各関係は対象名・`present`・出典ページ・引用文つき。`variants` は A/W 綴りの関係（根拠つき） |
| include/def 生成にどう使えるか | `generation_use`（`include-declaration` / `type-definition` / `link-library` / `def-export` / `abi-layout` / `unicode-mapping` / `version-scope` / `ce-restriction`）＋ `headers.tsv` / `libraries.tsv` / `dlls.tsv` / `modules.tsv` / `gaps.tsv` / `surface.tsv` |

方針として守っていること:

* **捏造しない。** 出典の無い値は入れません。CE に無い API を補完したり、
  Win32 の値を CE の値として流用したりはしません（流用は「Win32 参照」と明示）。
* **C のテキストを勝手に直さない。** 宣言は逐語。`spacing: "collapsed"` は
  ページ自身が空白を失っていることを示すフラグで、本文は修復しません。
* 派生値（`kind`、`doc_role`、`spacing`、`surface`、`variants_of`、
  `calling_convention`、要求の `field`/`key`）は Schema に「DERIVED」と明記し、
  元のラベル・原文を併記します。

## 8. 生成の試作（include/def の材料を実際に出す）

`tools/gen-include-def.py` は知識基盤の最初の消費者です。1 つの CE バージョンを
指定して、次を書き出します（出力先は git 管理外の `build/`。3 秒程度で再生成）。

```bash
python3 tools/gen-include-def.py --list
python3 tools/gen-include-def.py --set learn/windows-ce-5.0 \
    --out build/generated/wince50
python3 tools/gen-include-def.py --set chm/windows-ce-3.0 \
    --out build/generated/wince30 --no-borrow
```

CE 5.0 を対象にした今回の結果:

| 出力 | 内容 |
|---|---|
| `include/<Header>.h.fragment` 592 ファイル | そのヘッダの宣言を**逐語で** 15,524 件。各ブロックに出典ページ・ライブラリ・種類をコメントで付記。include ガードや並び順は生成側の仕事（断片であることを明記） |
| `link/<module>.def` 184 ファイル | モジュール別の EXPORTS 作業リスト（関数・コールバックのみ）4,382 行。`coredll.lib` と `coredll.dll` のような綴りは 1 モジュールにまとめ、元の綴りを先頭に列挙 |
| `manifest.tsv` | エンティティ ↔ `surface` ↔ ヘッダファイル/モジュール ↔ 宣言 ID ↔ 出典ページ ↔ `borrowed_from` ↔ バージョン |
| `report.md` | **境界の節**（CE 由来か Win32 由来か、流用件数）＋ 生成数と、できなかった理由の内訳 |

* 出力できなかった内訳: 宣言が無い 1,826 / ヘッダの記載が無い 1,168。
  `knowledge/reports/gaps.tsv` と同じ作業リストです。
* `.def` は**作業リスト**であり完成品ではありません。装飾名（`_Name@N`）・序数・
  エクスポートテーブルは文書に無いため、ファイル先頭にその旨を明記しています。

## 13. 追補（第 4 ラウンド後半）: 宣言を印刷しないページのメンバー情報と、`catalog-only` の裏取り

第 4 ラウンドの公開後に、知識基盤の事実を 1 種類増やしました。ページが
**宣言本体を印刷していなくても、メンバーを文書化している**場合があるためです。

* 実測: `corpus/win32/api/*.md` の 5,279 ページのうち **882 ページ**が
  `### -field` を持ち、そのうち **842 ページ**が `-struct-fields` 節
  （= 構造体のメンバー一覧。残り 40 ページは列挙値に同じ見出しを使うだけで
  一覧がない）です。この 842 ページのうち **840 ページが宣言フェンスを
  印刷していません**（宣言とメンバー一覧の両方を持つのは
  `WIN32_FIND_DATAA`/`W` の 2 ページだけ）。したがってこれらの構造体は
  「宣言なし」ではなく「**メンバー名と順序だけが事実としてある**」状態です。
* 対応: `tools/page_parse.py` が宣言テキストの**末尾**（`} MainAVIHeader;`）から
  識別子を読む `declared_names()` を追加し（タイトルの綴り合わせは誤検出するため
  使わない）、`tools/build-kb.py` が
  `documented_fields` / `documented_fields_page` として記録、
  `generation_use: abi-members` を付け、`knowledge/kb/struct-fields.tsv`
  （5,204 行 / 801 構造体）に書き出します。**オフセットはどのページも述べて
  いないので、記録も生成もしません**（`abi-layout` との区別）。
* 途中で 1 件の不具合を自分で見つけて直しました: 集約パスが
  `documented_fields` を上書きして 0 件になっていた（レポートが空、`abi-members`
  0）。修正後は 801 構造体・`abi-members` 251 件です。`tools/check-kb.py` に
  検査（ページの存在、`abi-*` の付与、`ce-name-lead` の形、`catalog-leads.tsv`
  への収載）を追加しました。

### `catalog-only` 3 件の裏取り（`knowledge/reports/catalog-leads.tsv`）

| 名前 | CE のページ | そのページが印刷する綴り | 構文ブロック | 読み |
|------|-------------|--------------------------|-------------|------|
| `AVIMAINHEADER` | CE 3.0 / 5.0 / .NET 4.x / 6.0 の「AVI Main Header」 | `MainAVIHeader` | 1 | CE は型を文書化している（綴りが Win32 と違うだけ）。なお `ms899420(v=msdn.10)` は CE 5.0 の名前一覧が指す ID だが、実ファイルは `corpus/learn/windows-ce-net-4x/`（CE .NET 4.x）にある |
| `MESSAGE` | 「#message (FMerge.exe)」 | （なし） | 0 | 名前一覧側のノイズ。CE のページはツールオプションの話題 |
| `SECTION` | 「/SECTION」 | （なし） | 0 | 同上 |

CE が印刷する綴りは `relations` の `ce-name-lead`（対象・ページ・根拠つき）と
して記録しました。**改名はしません** — `MainAVIHeader` が CE の実装名かどうかは
この資料では確定できないためです（リーンに残します）。

再現: `python3 tools/build-kb.py --workers 8 && python3 tools/check-kb.py`。
ページ数の実測は `grep -rl '^### -field' corpus/win32/api --include=*.md | wc -l`
（882）と、`knowledge/kb/struct-fields.tsv` の行数（5,204 = 801 構造体）で
確かめられます。
