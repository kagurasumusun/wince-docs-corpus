System Requirements

To use the Windows CE 5.0, you need:

  • 400-MHz Pentium II or later processor; 1-GHz processor recommended
  • Microsoft Windows 2000 Professional with Service Pack 4 or later, or Windows XP Professional with Service Pack 1 or later
  • Microsoft .NET Framework, version 1.1
  • 256 MB of RAM; 512 MB of RAM recommended
  • 1.7 GB of available hard-disk space for a typical single microprocessor installation; approximately 17 GB for installation of the entire product, including the Platform Builder for Microsoft Windows CE 5.0 toolset
  • VGA or higher-resolution monitor; Super VGA recommended
  • Microsoft Mouse or similar pointing device
  • Serial port or Ethernet card for debugging support; a LAN hub is recommended
  • CD-ROM or DVD-ROM drive

Installation

Windows CE 5.0 is distributed on multiple CDs or a DVD. The setup application, Setup.exe, copies the files from the CDs or DVD to the development workstation.

To install Windows CE 5.0

Note   To install Windows CE 5.0, you must have administrative privileges.
  1. Log on to the development workstation with Windows administrator privileges.
  2. If version 1.1 of the Microsoft .NET Framework is not installed on the development workstation, run Dotnetfx.exe to install the .NET Framework.

    You can find Dotnetfx.exe in the root directory of the first Windows CE 5.0 CD or in the root directory of the Windows CE 5.0 DVD.

  3. Run Setup.exe from the root directory of the first Windows CE 5.0 CD or from the root directory of the DVD.

    If autorun is enabled, Setup.exe runs when you insert the CD or DVD.

  4. When the Welcome dialog box appears, choose Install and follow the on-screen instructions.
    Note   To reduce the installation size of Platform Builder, in the Custom Setup dialog box, select only the microprocessors you need.

During installation, the progress bar is not always accurate, especially for larger installations with more than one CPU.

Installation times can vary according to installation type:

  • Tools-only installation: 15 – 20 minutes
  • Default installation (Tools, Test Kit, CEPC, and Emulator): 20 – 30 minutes
  • Full installation: 2 or more hours

  7. Choose OK.

Intel Mainstone II fails when using PC card NICS to transfer packet sizes that are approximately 55 KB or greater

This is due to the I/O cycle access latency. The I/O access cycle timing can be shortened and still be within PCCARD specification. However, the timing was made lax to accommodate PC cards that do not conform to the specification.

Debug serial port on the Intel Mainstone II Development Platform is now selectable

Intel uses the fully functional universal asynchronous receiver-transmitter (FFUART) for debug serial messages. In the Windows CE BSP implementation for the Intel Mainstone II Development Platform, the Bluetooth universal asynchronous receiver-transmitter (BTUART) is used to free the FFUART for production serial use. Instead of changing the port to the FFUART, which might break testing and break drivers that require a port with full hardware handshaking signals, the debug serial port was made to be selectable.

The default is to use the BTUART (front left on the main board). At 38400 N81, if you stop in the boot loader menu, you can change this to the FFUART and save your settings. After reboot, the newly selected port will be used. Regardless of the port chosen in the boot loader, this information is provided to the OS and the OS debug messages will use the boot loader settings.

Note   If you try the BTUART at 38400 N81, and do not see any debug output, try using the FFUART port on the CPU daughter card.

DBAU1xxx platforms show drift in GetTickCount

The crystal oscillator that is used for the system tick on the DBAU1x00 platforms runs at 32.768KHz. The prescaler used to divide that frequency into a reasonable system tick frequency is 33. Since the resultant value (oscillator freq / prescaler) is non-integral, users will notice a drift in the value returned by GetTickCount.

The real-time clock (RTC) on these platforms is derived from the tick count generated by the same clock-prescaler pair. Because the RTC routines attempt to compensate for this drift, the drift should be within statistical error.

KITL does not work over a serial connection on the NEC Solution Gear 2-Vr5500 Development Kit

The SG2-Vr5500 boot loader menu advertises that the universal asynchronous receiver-transmitter (UART) may be used for the debug connection, or KITL. Serial KITL does not work on the SG2-Vr5500 Development Kit. Use the default Ethernet connection instead.

Some BSPs do not support suspend/resume

The implementation of the OEMPowerOff function in some BSPs is stubbed, which means that suspend will immediately return. Although device drivers and Power Manager will be used, the device does not actually reduce or remove power to the various hardware subsystems.

The following BSPs do not support suspend/resume:

  • Intel Mainstone II Development Platform
  • SMDK2410 Samsung MCU Development Kit

The NEC Solution Gear 2-Vr5500 system tick and real-time clock (RTC) timers drift

The SG2-Vr5500 system tick and RTC timers' timebase can drift due to skew and jitter problems with the clock's phase-locked loop (PLL). A loss of 3 seconds occurs on the device over the course of 15 minutes. The timer drift can vary from one board to another. The drift affects the OS timer, which can handle this variance, and the RTC timer, which is derived from the OS tick counter and cannot handle the variance. If you require accurate RTC times, consider changing the RTC implementation to use the Dallas Semiconductor RTC on the main board.

Windows CE Test Kit disconnect timeout can be set using the registry

Developers can specify the timeout period after which a device that is not responding to communications calls is considered disconnected. A developer might use this setting, for example, when a test breaks into the debugger and they don't want the device to become disconnected while they debug the issue.

To use this setting, create a DWORD registry entry called Disconnect Timeout Seconds in the HKEY_CURRENT_USER\Software\Microsoft\CETT\WinCE 5.00 key. Set the value of this entry to the number of seconds the Windows CE Test Kit allows to pass before considering the device to be disconnected.

By default, devices are considered disconnected if the Windows CE Test Kit receives no response from the device within 60 seconds.

If the connection uses Windows Sockets, a sockets call may return an error that causes a disconnect more quickly than the value specified using this registry setting.

Device Management

Device Management checkpoint and restart registry settings

CheckPoint/Restart: MAX_RETRY times are variable

Device Management checkpoint and restart registry settings

The device management functionality in Windows CE supports the following checkpoint and restart registry settings. Both of these settings exist in the HKEY_LOCAL_MACHINE\Comm\ApplicationDownload key.

  • RetryTime is a DWORD setting that specifies the time between a failure and the next retry attempt. The setting should use the format yy-mm-dd hh-mm-ss. The default setting is 00-00-00 00:03:00, which causes a retry after three minutes have passed.
  • MaxRetry is a DWORD setting that specifies the number of retry attempts before a task is deleted. The default setting is five attempts.

CheckPoint/Restart: MAX_RETRY times are variable

Under some network error conditions, there may be a delay longer than the expected maximum (number of retries multiplied by retry time, as configured in the registry) before a task becomes current again. This is a temporary situation; the task will eventually continue as usual.

FIPS compliance

Federal Information Processing Standard (FIPS) is a standard that describes the requirements for hardware and software cryptomodules used in computer systems within the U.S. government. FIPS 140-1 (1994) and FIPS 140-2 (2001) are defined by the National Institute of Standards and Technology (NIST).

In Windows CE 5.0, the CAPI (Crypto API) Cryptographic Service Provider (CSP) implemented in the rsaenh.dll file is being submitted for FIPS validation. The following Windows CE cryptographic algorithms are eligible to receive FIPS 140-2 Level 1 certification:

  • AES
  • DES
  • 3DES
  • SHA-1
  • SHA-2
  • HMAC

Remote Desktop Protocol (RDP) uses the CSP and is eligible to receive FIPS compliance, pending certification.

To avoid this difficulty, you can write a simple keyboard mapping application that maps a pressed F5 key to 0xC2, or whatever you define as the virtual key code for your hotkey.

Use of Device Management Client to automatically update IP phone software

The IP phone design template is tested at Microsoft is by using Windows CE Device Management Client functionality. This functionality enables the phone software to be automatically updated without user intervention. The phone software is updated by shutting down the phone application, updating .EXE and .DLL files, and then restarting the application. In practice, this means that a new version of the phone software can be installed overnight while the user is away from the office.

User settings, which are stored in the registry and in Windows CE databases, are preserved. The update changes only files; it does not affect the contents of the registry or Windows CE databases. The following settings are preserved on the phone after update:

  • User credentials
  • Speed dial
  • Call logs
  • PIN number
  • Call forward numbers
  • Phone settings

Although Windows CE does not include the specific setup and files used in the Microsoft testing, it may be helpful to understand the basic testing process in case you want to do something similar with your IP phone. Because the Device Management Client is general functionality and not specific to IP phones, you can apply these steps to any Windows CE project.

The following software is used in Microsoft testing:

  • IP phone OS design that includes the Device Management Client (SYSGEN_DEVMGMT). This Sysgen variable is not included in the IP Phone design template.
  • Microsoft Systems Management Server 2003 (SMS 2003) with the beta Device Management Feature Pack.

For more information about Device Management Client functionality, see the Device Management Client topic in the Platform Builder documentation. For more information about SMS 2003, see the Microsoft MSDN® Web site.

During the Microsoft testing process, to update the phone application and related DLLs, the administrator and SMS installation script do the following:

  1. The phone system administrator creates a new SMS package that contains updated voipui.exe and other DLL files, and a custom SMS installation script, and makes this package available on the SMS server.
  2. The device management client on the phone periodically polls the SMS computer and sees that there is a new package for download.
  3. The device management client on the phone downloads the package and unpacks the files to a temporary directory on the phone.
  4. The device management client runs the custom SMS installation script, which takes the steps explained below in steps 5-8.
  5. The installation script runs a small application that displays a dialog to ask the phone user if they want to upgrade now or wait until later. If the user upgrades now, the application sends a WM_CLOSE message to voipui.exe. This causes voipui.exe (the TUI application) to exit so that voipui.exe and the DLLs used by voipui.exe can be updated.
  6. The installation script copies the new files from the temporary directory to the windows directory, overwriting the existing files.
  7. The installation script runs another small application that restarts voipui.exe.
  8. The installation script deletes the files from the temporary directory because they are now no longer needed.

The Device Management Client supports updating the entire run-time image. This functionality was not used while testing the IP phone code because the Broadcom BSP does not support writing the image to flash memory from within Windows CE (it supports writing to flash from the boot loader).

Microsoft updates the following files during internal testing:

  • voipstore.dll
  • voipui.exe
  • voipphonemedia.dll
  • rtcclient.dll
  • voipmanager.dll
  • voipconfigurationdatastore.dll
  • voiplap.dll
  • owaexchangeclient.dll

For example, rtcclient.dll is shipped as part of Windows CE and cannot be modified, and so would probably not be included in an update package. In contrast, voipui.exe is shipped in source form, can be modified, and probably would be included and updated.
