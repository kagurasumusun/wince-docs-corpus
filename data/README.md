# data/

Derived datasets about the corpus in `corpus/`. Nothing here is the
documentation itself; everything is either an official Microsoft TOC export
(`catalogs/`, `toc/`), a harvested expectation set (`manifests/`), an
extraction product (`metadata/`), a report (`reports/`) or a generated index
(`index/`).

```
data/
├── catalogs/   page_id <TAB> title               official TOC exports, one per set
├── toc/        depth <TAB> "Set :: Section :: …"  section trees of the books
├── manifests/  page_id <TAB> title               pages a complete harvest should contain
├── metadata/   per-page API metadata (JSON)
├── reports/    missing-pages.tsv                 catalog pages not present in the corpus
├── index/      INDEX.tsv, corpus.sqlite3         generated by tools/build-index*.py
└── logs/       fail-<queue>.log                  harvest failures (not committed)
```

## catalogs/

Official page-id → title tables, used for title fallback, set checks and gap
reports.

| File | Rows | Covers |
|------|-----:|--------|
| `windows-ce-3.0.tsv` | 8,962 | CE 3.0 documentation (`corpus/chm/windows-ce-3.0/`). |
| `windows-ce-5.0.tsv` | 22,918 | CE 5.0 product documentation. |
| `windows-ce-net-4x.tsv` | 6,363 | Windows CE .NET 4.x. |
| `windows-embedded-ce-6.0.tsv` | 23,760 | Windows Embedded CE 6.0. |

Ids are the same as the corpus file names (`aa450192(v=msdn.10)`), so a join
is just `basename(page.html)`. Caveat: a few ids were later re-used by
Microsoft for unrelated pages (for example the CE .NET catalog lists
`dd320882(v=vs.100)` as `IsValidPtrIn`, while Learn now serves a Visual Studio
topic under that id); such pages are kept in `corpus/learn/unclassified/`.

## toc/

Section tree of each book: column 1 is the depth, column 2 is the fully
qualified section path (`Windows CE 5.0 :: Product Documentation :: …`).
Useful for grouping pages by chapter even though the corpus itself is flat.

## manifests/

The page set a *complete* harvest of that set should contain
(`page_id <TAB> title`), i.e. the target lists used to measure harvest
progress: `windows-ce-5.0.manifest` (22,888) and
`windows-embedded-ce-6.0.manifest` (23,712). The difference against the
catalogs is explained in `reports/missing-pages.tsv`.

## metadata/

Per-page API metadata extracted from the harvested HTML, one JSON array per
file. Common fields: `id`, `title`, `sig` (printed syntax), `os`
("Windows CE 5.0 and later."), `header`, `lib`, `dll`, `params`, `notes`.

| File | Rows | Covers |
|------|-----:|--------|
| `api-windows-ce-3.0.json` | 8,962 | CE 3.0 (adds a `versions` field). |
| `api-windows-ce-net-4x.json` | 6,361 | Windows CE .NET 4.x. |
| `api-windows-ce-5.0-6.0.json` | 18,150 | CE 5.0 (16,771 pages), CE 6.0 (1,377) and 2 CE .NET pages. |
| `api-struct-prints.json` | 80 | struct/union definitions for the pages where a second extraction pass was needed (`print_kind`, `print_tree`, `source_row` fields). |

These were produced by the companion `wince-api` tooling (`tools/ce3-collect.py`
and friends) and are kept here as data, not regenerated by the scripts in
`tools/` of this repository.

## reports/

`win32-shared.tsv` — the Win32-common API surface:
`name <TAB> ce_sets <TAB> ce_page_ids <TAB> win32_pages`, one row per shared
API name (5,009 rows). Joins a CE API name to the catalog page ids that
document it and to the page(s) imported under `corpus/win32/api/`.

`win32-imported.tsv` — one row per imported Win32 page
(`path <TAB> module <TAB> kind <TAB> name <TAB> ce_shared <TAB> ce_sets`),
17,095 rows; `ce_shared=yes` for the 5,219 pages whose name is in a CE
catalog, `no` for the module-context pages.

Both are generated by `python3 tools/build-win32-map.py`.

`duplicates.tsv` and `corpus-problems.tsv` — the output of
`python3 tools/check-corpus.py --report`: byte-for-byte duplicate groups
(`md5`, `size`, `n`, `paths`) and everything that does not look like a page
(unindexed/empty/unreadable files, non-UTF-8 bytes, HTML without `</html>`,
index rows whose file is gone). At the 2026-10 check the findings are the
known pairs: one CE 1.0 book page that shipped twice on its CD
(`PEGSDK/AB30G.html` = `AB93G.html`) and 31 duplicate groups inside the CE 5.0
component CHMs (`wcemouse5` and `wcestylus5` share their mouse/stylus pages,
etc.) — both are the media's own structure, not an extraction error, so they
stay. Everything else is clean: 0 empty/unreadable files, 0 non-UTF-8, 0
pages without `</html>`, 0 duplicate content.

The checker also reports how many pages belong to each index (`INDEX.tsv`,
`corpus.sqlite3`) and compares them with the files on disk; run it after any
harvest or import.

`crawl-last.txt` — what the last mirror crawl did (which pages it stored, what
it skipped and why it stopped), for the same reason: the runner's job log is
not readable from here, and a crawl that dies half way through commits its
pages anyway.

`media-last.txt` — what the last `import-media` run did (`queues/media.tsv`,
`.github/workflows/import-media.yml`): which medium it fetched, what the
inventory found, which documentation files it imported, and the reason when a
step failed. The runner's job log is not readable from the environment this
corpus is maintained from, so the run commits its own output.

`wayback-status.tsv` — what the harvester learned about the Wayback queue:
one row per topic (`page_id`, `status`, `checked`, `snapshot`).

* `stored` — the page is in the corpus.
* `resolved` — the pinned capture date did not work, but the availability API
  named a capture that did; the URL it returned is in the last column.
* `not-archived` — the Internet Archive has no capture of that topic at all;
  it is skipped without further requests (the queue stays as a record).
* `covered` — the topic is already in the corpus from another tree (in
  practice the learn.microsoft.com harvest), so the MSDN rendering would be a
  duplicate; skipped without a request.

`harvest-last.json` / `harvest-history.tsv` — what the last harvester run did
(counters plus a `fail_log.statuses` breakdown from `tools/harvest.py
--summary`, written by the workflow) and one
row per run (`finished`, `queue`, `lines`, `stored`, `skipped`, `failed`,
`invalid`, `robots`, `interstitial`, `requests`, `elapsed_seconds`), appended by
`python3 tools/summarize-harvest.py`. They are how a scheduled run's progress
is audited without reading the job log.

`missing-pages.tsv` — catalogued pages that are not present in the corpus,
regenerated by `python3 tools/build-gap-report.py` (`page_id`, `title`,
`source_catalog`, with a header row).

As of the 2026-10 re-organisation the corpus is complete against three of the
four catalogs (CE 3.0, CE 5.0 and CE 6.0 all 100 %); the report contains a
single row:

```
dd320882(v=vs.100)  IsValidPtrIn  windows-ce-net-4x
```

This is a page-id artefact rather than a missing topic: the CE .NET catalog
lists `dd320882(v=vs.100)` for `IsValidPtrIn`, but Learn now serves an
unrelated Visual Studio topic under that id, so the harvested copy lives in
`corpus/learn/unclassified/` while the CE .NET full-text search finds
`IsValidPtrIn` in `ms885895(v=msdn.10)`.

(The previous report, a 3,641-row to-harvest list predating the last harvest
runs, is superseded by this regenerated file; it remains available in the git
history.)

## index/

Generated, committed so tools and the harvester's resume check do not have to
rescan ~78k HTML files.

* `INDEX.tsv` — `# id <TAB> book <TAB> path <TAB> title`, one row per page
  (130,185 as of 2026-10). `book` is the corpus-relative directory
  (`learn/windows-ce-5.0`, `win32/api/fileapi`, `chm/windows-ce-3.0`,
  `mvb/windows-ce-1.0/PEGSDK`).
  Titles come from `<title>` (HTML) or the `title:` front matter (markdown),
  falling back to the catalogs. Regenerate with
  `python3 tools/build-index.py`.
* `corpus.sqlite3` — SQL index:
  `pages(path, page_id, section, title, size)` (keyed by path: page ids repeat
  across sdk-api modules, e.g. `CreateFileA`/`CreateFileW` variants) and
  `names(name, page_id, kind)` with
  `kind ∈ {title, api, const, proto, struct, enum}` — `api` rows come from the
  markdown pages, the others from the HTML print patterns; HTML pages whose
  title is a bare identifier (`CreateFile`, `BM_CLICK`, `hostent`) contribute a
  `title` name when the page also writes it like a symbol, which is what makes
  the CE 1.0/3.0 and Windows Mobile pages searchable with `tools/find-api.py`
  — plus a `meta` table holding the incremental state.
  Refresh with `python3 tools/build-index-sql.py` (`--full` to rebuild).

## crawl/

Progress of the documentation-mirror crawls (`tools/crawl-mirror.py`):
`<name>.json` records every URL already fetched and the book folders learned
from the site's table of contents, so a crawl can be split across runs and a
finished tree is not fetched twice. Committed on purpose (the runner starts
from a clean checkout).

## logs/

Harvest failure logs (`fail-<queue>.log`, tab-separated `status <TAB> url`),
written by `tools/harvest.py`; `*.log` is git-ignored. The harvester retries
non-404 entries once at the end of a run; `wayback-interstitial` entries are
kept out of that retry pass (the URL only has the Internet Archive's
"JavaScript required" notice, not a capture).
