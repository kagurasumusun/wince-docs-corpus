About Card Services

Card Services establishes the interface between the PC Card hardware and the other software in the system. Card Services has a set of functions defined for accessing its services. Drivers use these functions to register their callback functions and set the event masks used to trigger the callbacks. Card Services monitors the status of the PC Card and uses the callback functions to notify the Device Manager and the PC Card driver of the events associated with a change of PC Card Status. Other Card Services functions obtain information from Card Services and set the PC Card operating parameters.

It is possible for a PC Card to have more than one function. Because of this, Card Services uses a socket number and a function number combination (specified with the CARD_SOCKET_HANDLE structure) to identify a particular function (also called a logical socket). The Card Services design lets function-specific drivers to be platform independent because it hides the details of the target hardware behind a well-defined software interface. The Card Services driver provides the interface between a function-specific driver and the system.

Card Services exports a set of functions that let a driver communicate with the PC Card. A set of functions let a driver interrogate PC Cards for tuple information and configuration data and configure them. Drivers also register callback functions with CardRegisterClient to be notified of PC Card status events such as card insertions and removals. When the Card Services senses a card status event, it calls the driver's status callback function so that the driver can perform the tasks required to service the specific event.

Similarly, if a device uses interrupts for operation, the driver uses CardRequestIRQ to register an I/O interrupt callback function. An I/O interrupt callback function is necessary only for I/O PC Cards (for example, memory PC Cards do not use interrupts). Card Services calls the registered driver's callback function when these card interrupts occur.

The Device Manager also registers its own status callback function with the Card Services to handle card events. So, the Device Manager is a client waiting for card notification events for PC Card and card removals.

Registering a Driver with Card Services

A driver uses CardRegisterClient to register a PC Card event callback function with Card Services. When PC Card events occur, such as CE_CARD_INSERTION, Card Services calls the driver’s callback function and passes it the event type. (Card Services will callback all drivers when a multifunction card is inserted.) The driver then determines how to respond. In the card insertion case, the driver determines whether it can control the inserted PC Card. In addition, the CE_CARD_INSERTION callback includes a pointer to the card's Plug and Play identification string (PnpID) in one of the parameters.

When driver uses CardRegisterClient, it specifies a globel event mask to indicate the type of events the driver wants to be notified about. If a driver wants to associate a socket and function pair with an event mask, it uses CardRequestSocketMask to define the association and event mask. The driver uses CardReleaseSocketMask to disable the event callback associated with the socket and function pair. If necessary, a driver can obtain the current masks with CardGetEventMask or change them with CardSetEventMask.

Before a driver terminates, it calls CardDeregisterClient to have Card Services discontinue servicing its callback and release any resources Card Services might have allocated to support the driver.

Mapping Device Memory--Device Reading and Writing

When a driver determines it wants to service a card, it uses Card Services to map system memory and I/O space to the PC Card's memory and I/O space. The dirver use CardRequestWindow to allocate a window. The window must be mapped by CardMapWindow before the window can access the PC Card. If needed a driver can change the attributes of a memory window with CardModifyWindow. When a driver is finished with a window, it releases it with CardReleaseWindow.

Interrupt-Driven Devices

In addition to registering a callback function with CardRegisterClient, the driver for an interrupt-driven I/O card must specify an interrupt request routine (actually, this is another callback function) using CardRequestIRQ. Card Services calls a driver's interrupt request callback when a real interrupt occurs on the card it is controlling. If there are multiple functions on a card, the interrupt request routine will be called only when an interrupt occurs on the requested socket/function pair.

The CardReleaseIRQ function stops notification of interrupts on the specified socket and function pair.

Tuple Information

Card Services provides several functions for reading tuple information from the card information structures (CIS). A driver can specify the type of tuple it wants and retrieve the first tuple for a socket and function with CardGetFirstTuple. Subsequent tuples are obtained with CardGetNextTuple. A driver uses CardGetTupleData function to read the data from the current tuple and it uses CardGetParsedTuple to read and parse a specified tuple.

Configuring and Accessing Socket and Function Pairs

A driver obtains the current status of the specified socket and function pair with CardGetStatus. If necessary, it changes the configuration with CardRequestConfiguration. This function configures socket attributes, interface type, voltage, and registers. When a driver is finished with the configuration, it uses CardReleaseConfiguration to place the selected socket and card into a memory only interface, the default mode. A driver can read or write the function and configuration registers of a PC Card with CardAccessConfigurationRegister. The CardResetFunction function resets a specified function in the specified socket.

If a driver needs exclusive access to a socket and funtion pair, it uses CardRequestExclusive to request the access. When finished with exclusive access, it uses CardReleaseExclusive to release access.
