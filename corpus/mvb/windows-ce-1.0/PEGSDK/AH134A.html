Shasm Release Notes

Differences from the Standard Hitachi Assembler

Shasm generates output in MS-COFF (the Microsoft variant of COFF), as compared to the Hitachi assembler, which generates output in SYSROF. Limitations of the MS-COFF format result in certain features of the Hitachi assembler being restricted or unavailable in Shasm. These restrictions are detailed in the following sections; here is a summary:

· Cannot currently import and export constant symbols defined with .EQU. Only label symbols and relative .EQU symbols can be imported and exported. This restriction may be lifted in the future.

· Symbols from a DUMMY section cannot be exported. This restriction may be lifted in the future.

· Alignments greater than 64 are not supported.

· The COMMON section type is not supported.

· The STACK section type is supported as if it were a regular DATA section.

· Absolute sections are not supported.

· Cannot specify an entry point using the .END directive.

· Any expressions (arithmetic) involving relative symbols must be reducible (by computing subparts of the expression whose operands are known at assembly time) to one of the following forms:

expr:	   constant

| symbol

| expr + expr

| expr - constant

Shasm generates error and warning messages that contain not only an error number (which in some cases is similar to the error or warning number used by the Hitachi assembler in the same situation), but also a descriptive message, which may include specifics relating to the particular instance of the error or warning. For example, the error message issued when a number is outside of the permitted range will tell you the illegal number (in both decimal and hexadecimal), along with the legal range.

There are several differences relating to assemble listings:

· Shasm does not show accumulated line numbers in the listing; it only shows the source line numbers. (If the lack of this “feature” is an issue, it could be implemented. However, the assemble listing seems much more readable without these extra numbers.)

· The default number of columns for the Hitachi assembler listing is 132; the default for Shasm’s listing is 80. However, Shasm does not truncate the source lines in the assemble listing, regardless of the number of columns.

· The Hitachi assembler shows machine code and data up to 8 bytes to a line. By default, Shasm displays the data 4 bytes to a line; you can use the -wide command line option to select the alternate behavior (up to 8 bytes per line).

· The Hitachi assembler is able to include a cross-reference list and section list in the listing file, and does so by default. Shasm does not currently support either the cross-reference list or the section list. (If the lack of this feature is an issue, it could be implemented.)

Assembler Directives New in Shasm

The following directives exist only in Shasm; they are not supported by the Hitachi assembler, except as noted.

.ERROR (and .AERROR)

.COMMON

.WEAK

.ERROR (and .AERROR)

Shasm introduces the .ERROR directive, which may be used to report errors detected at assembly time by user code. If a .ERROR directive is assembled, its operands (if any) are evaluated, the results concatenated, and the result of the concatenation is used as the error message. The operands may have either string or numeric values. Note that Version 2.0 of the Hitachi assembler introduces a .AERROR directive, which has a similar function (although it may not have operands). Shasm supports .AERROR identically to .ERROR. Example:

.section .text

.org 0x202 ; force the .error to be assembled

.aif $ - .text > 0x200

.error “PC overflow: is ”, $, “, expecting < ”, 0x200

.aendi

.COMMON

Shasm introduces the .COMMON directive, which may be used to define a symbol that should be initialized to zero unless some other object file calls for it to be initialized to a specific value. This extension is necessary to support the equivalent of (and assemblable listing for) C code such as:

int a;

which in external (file) scope means that if no other file defines and initializes variable a, then a should be placed in the .bss section, which causes it to be initialized to 0. If another file defines a, such as:

int a = 5;

then both files will refer to the same variable a, which will be initialized to 5, and no link error will result. Note that this works differently in C++; in C++, the above example would require a link error.

Shasm provides the .COMMON directive to implement this concept. The syntax of the .COMMON directive is as follows:

.common	<symbol_name> [, <size>]

where symbol_name is the name of the symbol to define, and size is the number of bytes that the data occupies. The size is optional; if omitted, it defaults to 0. Examples:

.common	_foo,4

.common _bar,2

.common __fltused

is equivalent to this C code:

int foo;

short bar;

void f (void)

{-

float a = 4.5; // force __fltused symbol

}

.WEAK

Shasm introduces the .WEAK directive, which may be used to define a “weak external” symbol. Weak externals are a mechanism for programs allowing flexibility at link time. A .WEAK directive such as:

.weak		unlink,__unlink

indicates that when the program is linked, if the symbol “unlink” is defined by any object file, then references to “unlink” are resolved to its definition as usual. However, if the symbol “unlink” is not defined by any object file, then references to “unlink” are resolved to “__unlink” instead. (The symbol “__unlink” must be defined in exactly one of the object files, or an error will result.) The syntax of the .WEAK directive is as follows:

.weak		<weak_name>, <default_name> [, <type_expr>]

The optional type_expr argument is an expression (whose value must be absolute), giving the type of weak external. If the value is zero or the third argument is omitted, the “alias” type of weak external is generated. This is almost certainly what you want; therefore, you would not ordinarily want to use the optional third argument. Examples:

.weak		foo,bar,1

NO_SEARCH .equ 1

SEARCH_LIB .equ 2

.weak ick,yuk,NO_SEARCH

.weak snap,crackle,SEARCH_LIB

Note that if you inadvertantly place a symbol in the third argument position, and the symbol happens to be relative, you’ll get error 404; this does not mean that you can’t use relative symbols or expressions in a .WEAK directive, just that the third argument has to have an absolute value.

Note that the C and C++ compilers prepend a _ (an underscore) to each symbol name; consequently, if unlink and __unlink were defined and referenced in assembly language, you would code the .WEAK directive as shown in the first example, above, but if unlink and __unlink were defined and referenced in C code, you would code the .WEAK directive as follows:

.weak		_unlink,___unlink

Function-Definition Assembler Directives

To support the requirements of structured exception handling and providing stack traces in the debugger, object files must contain information regarding where functions begin and end, and what part of each function is devoted to setting up the function’s stack frame. For functions written in C and C++, this is handled by the compiler, and need not be a concern of programmer. However, when coding in assembly language, the programmer is responsible for providing this information. You provide this information using the following directives:

.PDATA: defines the language specific exception handler, and optionally data for that handler, for the following or current function.

.ENTRY: defines a function and marks its beginning.

.BIGENTRY: same as ENTRY but only used for exceptional situations.

.PROLOG: marks the end of the function prolog. The function prolog is the code at the beginning of the function that sets up the function’s stack frame, in accordance with the Calling Standard Specification.

.ENDF: marks the end of the function.

For more detailed information on prolog code and related topics, refer to the Calling Standard Specification document; here, we are primarily concerned with the syntax and semantics of the relevant assembler directives. Note that it is recommended that you use the calling convention macros described in the Calling Standard Specification, rather than using these directives yourself; these macros are summarized following the description of the directives.

.PDATA

The .PDATA directive specifies a language specific exception handler for the following or current function. Beginning with Shasm version 3.00.6070, the .PDATA directive must appear before the .ENTRY or .BIGENTRY section to which it applies. (Previously, the .PDATA directive could appear before or after the .ENTRY directive, as long as it appeared before the .ENDF directive. This is no longer the case; it must now precede the .ENTRY or .BIGENTRY directive.) The exception handler should be the address of a function, although no warning or error will be issued for a non-relative operand. You may optionally also provide one longword (4 bytes) of data for use by the exception handler; depending on the handler, that data may also be a pointer (an address). The syntax of the .PDATA directive is as follows:

.pdata	<handler_address> [, <handler_data>]

where handler_address and handler_data may be expressions of any sort. Forward references and relative values are permitted. Note that the .PDATA directive is not persistent; it applies to no more than one function. To specify an except handler (and optionally handler data) for more than one function, you must provide a .PDATA directive for each such function. Also, function information (including information supplied by .PDATA directives) is maintained separately for each section. The .PDATA directive is optional; Shasm issues no error or warning messages if it is not supplied. Examples:

.section	.text

.import ex_handler

.import handler_data

; set up exception handler for following function (fun1 in

; this case).

.pdata ex_handler,handler_data

fun1: .entry

.prolog

rts

nop

.endf

; fun1 uses ex_handler & handler_data.

fun2: .entry

.prolog

rts

nop

.endf

; fun2 has no exception handler or handler data (both 0).

.pdata ex_handler

fun3: .entry

.prolog

rts

nop

.endf

; fun3 uses ex_handler; handler data is 0 (the default).

.pdata fun4,5

fun4: .entry

.prolog

rts

nop

.endf

; fun4 is its own exception handler (probably a bad idea);

; handler data is a constant 5.

fun5: .entry

.prolog

rts

nop

.endf

.pdata ex_handler

; fun5 has no exception handler or handler data; the .pdata

; directive above applies to the next function. (The assembler

; issues a warning if no function follows in the same section,

; since in that case the .pdata directive would have no effect.)

.ENTRY

The .ENTRY directive marks the beginning of a function, and associates a name with that function. You should insert an .ENTRY directive before the first line of code (.DATA and related directives are fine). If Shasm encounters code before any .ENTRY (or after a .ENDF, with no intervening .ENTRY), it will issue a warning, and act as though a .ENTRY directive had been found immediately before the line of code. The syntax of the .ENTRY directive is as follows:

<label>	.entry

The label operates as a normal label (it causes the symbol to be defined with the current value of the location counter as the value of the symbol); it also associates the symbol with the function. See the examples for the .PDATA directive, above.

.BIGENTRY

The .BIGENTRY directive has the same purpose and syntax as the .ENTRY directive. Ordinarily, you should use the .ENTRY directive. For functions that are more than 16,777,214 bytes long, or whose prolog is more than 510 bytes long, you should use the .BIGENTRY directive. If you try to use .ENTRY for a function that needs .BIGENTRY, Shasm will issue error 554 or 555. If you use .BIGENTRY for a function that could use .ENTRY, no warning or error will result, and the output will be correct; however, this wastes 8 bytes in the code section in which the .BIGENTRY directive appears. Note that a function that required the use of .BIGENTRY would be very unusual.

.PROLOG

The .PROLOG directive marks the end of the prolog code of a function. The prolog code is the code at the beginning of a function that sets up the stack frame for the function, in accordance with the Calling Standard Specification. This would include saving the PR register, pushing other registers onto the stack, setting up the frame pointer, etc. See the Calling Standard Specification for more information. The .PROLOG directive should appear between the last line of prolog code and the first line of non-prolog code for the function. If the function has no prolog code, then the .PROLOG directive should appear between the .ENTRY directive for the function and the first line of code in the function. The syntax of the .PROLOG directive is as follows:

.prolog

Example (see also examples for the .PDATA directive, above):

fun6:	.entry

; this is the prolog code:

mov.l r14,@-sp

mov.l r8,@-sp

sts.l pr,@-sp

mov sp,fp

add #12,fp

; end of prolog code.

.prolog ; mark end of prolog code

add #-16,sp

; function code goes here

mov fp,r2

add #-12,r2

lds.l @r2+,pr

mov.l @r2+,r8

mov r2,sp

rts

mov.l @sp+,fp

.endf

Notes: it is important that the .PROLOG directive be used appropriately, and that the prolog code (and the epilog code) of each function conform to the Calling Standard Specification. Otherwise, structured exception handling may not work correctly, and the debugger may be unable to provide stack traces. If the .PROLOG directive is not specified for a function (ie, an .ENDF directive is encountered without a .PROLOG directive having been encountered since the most recent .ENTRY directive), Shasm will issue a warning, and act as though the .PROLOG directive had been specified immediately following the .ENTRY directive. This effectively indicates that the function has no prolog code; if the function does in fact have prolog code, then structured exception handling and stack tracing may not operate properly, as noted. It is recommended that you always use a .PROLOG directive, even if the function has no prolog code.

.ENDF

The .ENDF directive marks the end of a function; it should appear after the last line of code for each function. If a .ENDF directive is encountered when there is no matching .ENTRY directive (ie, if no .ENTRY directive has been encountered, or no .ENTRY directive has been encountered since the most recent .ENDF directive), Shasm issues an error message. If the end of the program (or section) is reached, and a function is still pending (either because there is a .ENTRY directive with no matching .ENDF directive, or because code was encountered without a .ENTRY directive, and so Shasm implicitly opened a function), Shasm issues a warning message and acts as though there were a .ENDF directive at the end of each section that has a pending function. The syntax of the .ENDF directive is as follows:

.endf

See the examples for the .PDATA directive.

When Shasm encounters an .ENDF directive, it writes out any pending literal pool for the current section (as if a .pool directive had been encountered). It also takes any pending .PDATA directive information, applies it to the current function (the one being terminated by the .ENDF directive), and resets the .PDATA directive information.

Calling Convention Macros

It is strongly recommended that you use the calling convention macros, rather than directly using the relevant assembler directives. These macros are documented in detail in Appendices A and D of the Calling Standard Specification, and their definitions are provided in the header file kxsh3.h, which may be used via the .INCLUDE directive. The following is a brief overview of the macros. See also the examples that follow.

START_REGION NameBegin

END_REGION NameEnd

These two macros are used to mark the beginning and end of a contiguous range of text or data. NameBegin labels the beginning of the range and NameEnd labels the end. Both of these names are in the global name space.

NESTED_ENTRY Name[,[Section=]SectionName]

Declares the beginning of a routine that either has an existing frame or creates a stack frame. Name is the routine name and is in the global name space. SectionName is the name of the section in which the entry will appear; it is optional and defaults to .text. A NESTED_ENTRY must have an associated PROLOG_END and ENTRY_END.

LEAF_ENTRY Name[,[Section=]SectionName]

Declares the beginning of a routine that does not require any prolog code. Name is the routine name and is in the global name space. SectionName is the name of the section in which the entry will appear; it is optional and defaults to .text. A LEAF_ENTRY must have an associated ENTRY_END. An explicit PROLOG_END is not needed in this case because LEAF_ENTRY includes PROLOG_END. Not all leaf routines can use LEAF_ENTRY.

ALTERNATE_ENTRY Name[,[Section=]SectionName]

Declares an alternate entry to a routine of either NESTED_ENTRY or LEAF_ENTRY type. Name is the entry point and is in the global name space. SectionName is the name of the section in which the entry will appear; this parameter is not used by the ALTERNATE_ENTRY macro, but is accepted and ignored for consistency with NESTED_ENTRY and LEAF_ENTRY. If used, an ALTERNATE_ENTRY call must appear in a routine's body.

ENTRY_END [Name]

Ends the current routine that was specified by a prior NESTED_ENTRY or LEAF_ENTRY. Name should be the same name used in the NESTED_ENTRY or LEAF_ENTRY macros; it is currently ignored by the ENTRY_END macro.

EXCEPTION_HANDLER Handler

Associates the exception handler Handler with the subsequent NESTED_ENTRY or LEAF_ENTRY routine. This association is in effect until the matching ENTRY_END macro is encountered.

EXCEPTION_HANDLER_DATA Handler,HandlerData

Associates the exception handler Handler and the HandlerData with the subsequent NESTED_ENTRY or LEAF_ENTRY routine. This association is in effect until the matching ENTRY_END macro is encountered.

PROLOG_END

Marks the end of the prolog area. This must appear following a NESTED_ENTRY or LEAF_ENTRY macro, following the prolog area and prior to the matching ENTRY_END macro.

NESTED_BIGENTRY Name[,[Section=]SectionName]

The same as NESTED_ENTRY, except uses the .bigentry assembler directive instead of the .entry assembler directive. Use this for functions that are more than 16,777,214 bytes long, or whose prolog is more than 510 bytes long. (Such a function would be very unusual.)

LEAF_BIGENTRY Name[,[Section=]SectionName]

The same as LEAF_ENTRY, except uses the .bigentry assembler directive instead of the .entry assembler directive. Use this for functions that are more than 16,777,214 bytes long. (Such a function would be very unusual.)

Calling Convention Macro Examples

For example, instead of writing:

.section	.text,code

.align 4

.global fun7

fun7: .entry

.prolog

rts

nop

.endf

.section special,code

.align 4

.global fun8

.pdata ex_handler

fun8: .entry

sts.l pr,@-sp

.prolog

bsr fun7

nop

lds.l @sp+,pr

rts

nop

.endf

You could simply write:

LEAF_ENTRY fun7

rts

nop

ENTRY_END

EXCEPTION_HANDLER ex_handler

NESTED_ENTRY fun8,Section=special

sts.l pr,@-sp

PROLOG_END

bsr fun7

nop

lds.l @sp+,pr

rts

nop

ENTRY_END
