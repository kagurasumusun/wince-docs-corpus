Functions, Macros, and Structures Used in "Hello Windows CE"

The following are brief explanations of the functions called in the “Hello Windows CE” sample program that differ from the standard Windows programming model. The functions that exhibit the same behavior as their Windows 95 counterparts are excluded from this discussion.

The Windows CE WinMain Function

As with other Windows-based programs, the WinMain function is the entry point to all applications written for Windows CE. The Windows CE WinMain function accepts the same four parameters as in other Windows-based programs with the following minor deviations:

· hInstance. The handle to this instance of the program. This parameter is identical to the corresponding parameter in other Windows-based programs.

· hPrevInstance. This parameter is obsolete for Windows CE and should always be NULL.

· szCmdLine. Command line parameters. For Windows CE this parameter is a pointer to a wide string to accommodate UNICODE. The type has been changed from LPSTR to accept a LPWSTR.

· nCmdShow. A flag indicating how the window should be displayed. Windows CE does not support all of the nCmdShow flags supported by Windows 95. A description of the flags can be found in the WinMain function section of the reference.

Registering the Window Class for Windows CE

Before an application window can be created you must first register a window class with the system by calling RegisterClass. Windows CE does not support all of the fields in the WNDCLASS structure used to define the characteristics of the window. The unsupported fields should be set to NULL. The unsupported fields are:

· style. Windows CE supports only one class style.

· hCursor. Obviously not needed because there is no cursor.

· lpszMenuName. Windows CE does not support default menus.

For more about the WNDCLASS structure see the "Structures" section of the reference.

Initializing Common Controls

The InitCommonControls function ensures that the common control DLL is loaded for the command bar.

Creating the Window

The CreateWindow function specifies the details of your window's appearance and functionality. The parameters for CreateWindow are the same for Windows 95 and Windows CE; however, it is best to use defaults for the initial size and position parameters.

Painting the Window and The Message Loop

The functions for painting the window, CreateWindow, ShowWindow, and UpdateWindow, along with the message loop functions, GetMessage, TranslateMessage, and DispatchMessage, exhibit functionality common to all Windows-based programs.

The Window Procedure

The window procedure, WndProc, contains some functions specific to Windows CE and some common Windows programming functions that have special implications for Windows CE.

WM_CREATE

As in Windows 95–based programs, messages are processed in the window procedure. When the WM_CREATE message is received by the “Hello Windows CE” program, two functions unique to Windows CE are called, they are:

· CommandBar_Create. This function creates an empty command bar. A handle to the instance of this window obtained in WinMain is passed to the function and it returns a handle to the command bar.

· CommandBar_AddAdornments. This function adds the close button to the command bar. When the close button is selected the system generates a WM_CLOSE message. The CommandBar_AddAdornments function can also be used to add a help button that generates a WM_HELP message and/or an OK button that generates a WM_COMMAND message with IDOK as the message identifier.

The “Hello Windows CE” program also calls the sndPlaySound function when the window is created. It plays a .wav file that is one of the sound files bundled with the applications and stored in ROM. Using the .wav files stored in ROM saves space in the object store. Because the sound is registered with Windows CE, the program can refer to that sound by the name of the .wav file.

Windows CE can support 16-bit .wav files, but some HPCs may not. Using 16-bit sounds in your application is not recommended. 8-bit mono sounds at 11,025 Hz or less are recommended to save storage space and processing time.

WM_PAINT

The WM_PAINT message informs the program when the client area of the window needs to be repainted. The sample program calls five functions in the WM_PAINT branch of the switch statement: BeginPaint, GetClientRect, CommandBar_Height, DrawText, and EndPaint.

The functions BeginPaint and EndPaint operate the same for Windows 95–based and Windows CE-based applications. BeginPaint prepares the window for painting and returns a handle to a device context, in this case the video display device driver. The EndPaint function releases the handle to the device context.

The GetClientRect function is called to obtain the dimensions of the client area of the window. It performs identically to its Windows 95 counterpart; however, because the command bar is in the client area, it must be accounted for before the dimensions are passed to DrawText.

The CommandBar_Height function returns the height in pixels of the command bar. The “Hello Windows CE” program implements the CommandBar_Height function by adding the value returned to the top of the rectangle obtained from GetClientRect.

DrawText is called to display “Hello Windows CE!” in the remainder of the client area. The flags passed in as the last parameter to this function specify how the text will be formatted on the screen. In this case they specify a single line of text centered in the rectangle passed in as the fourth parameter.

The TEXT Macro

Several of the functions used in “Hello Windows CE” accept text strings as parameters. These functions use the Win32 TEXT macro that forces the compiler to convert ANSI characters to Unicode characters. For example, passing the ANSI string 'Hello Windows CE!' through the TEXT macro converts it to 16-bit wide characters.

Unicode is the native code set for Windows CE. Unicode establishes a unique 16-bit code for over 65,500 characters, a big improvement over ANSI's standard 8-bit code capable of representing only 256 characters. Unicode adds flexibility and portability to your applications. The tradeoff however, is that text stored by your program takes up twice as much space in the object store.
