5.2 Assembler Section and Location Counter Directive Reference
5.2.1 .SECTION: Section Declaration
5.2.2 .ORG: Location Counter Value Setting
5.2.3 .ALIGN: Location Counter Value Correction
The assembler provides the following directives for sections and the location counter:
.SECTION: Declares a section
.ORG: Sets the value of the location counter
.ALIGN: Adjusts the value of the location counter to a multiple of the boundary alignment value
5.2.1 .SECTION: Section Declaration
Syntax
.SECTIOND<section name> [,<section type> [,<section attributes>...]]
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .SECTION mnemonic in the operation field
· Operands: First operand: the section name; the rules for section names are similar the rules for symbols, except that the first character of the section name may be a period (.), and except as noted below for comdat support. (See section 2.5.2, Symbol Coding)
Second operand: the section type; when the specification is omitted, the section will be a code section (Table 5.2)
Table 5.2 Second Operand Section Types
Attribute		Section Type
CODE (default)Code section
DATAData section
BSSBSS section
DUMMYDummy section
· When the specification is omitted, the section will be a code section
Third operand: section attributes (Table 5.3)
Table 5.3 Third and Greater Operand Section Attributes
Specification		Meaning
SELECTION=<selection number>Specifiy comdat selection type
ASSOC=<section symbol>Specify other section to associate with
ALIGN=<boundary alignment value>Specify section's alignment
Note: When the specification is omitted, the section will be a relative address section with a boundary alignment value of four.
Description: .SECTION is the section declaration assembler directive. A section is a part of a program, and the linkage editor regards it as a unit of processing. Figure 5.1 describes section declaration using simple examples.
Figure 5.1 Section Declaration Assembler Directive
A section name (both in a .SECTION directive and in expression contexts) may be either of the same form as an ordinary symbol (with the extension of allowing a period (.) as the leading character of the name), or of the following form:
<symbol1> {- <symbol2> }
In the example above, symbol1 is the section name as it should appear in the object file, and symbol2 is the “COMDAT symbol” as described in the MS-COFF documentation. The curly braces are part of the actual syntax. A section declared using this syntax will be a COMDAT section in the object file. A section is uniquely identified by the combination of symbol1 and symbol2. For instance, .text{-foo} and .text{-bar} will identify two different sections; both will have the name .text in the object file, and both will be combined into a single .text section (along with all other .text sections) at link time. However, the former will have foo as its COMDAT symbol and the latter will have bar as its COMDAT symbol.
The SELECTION=<expression> option determines the COMDAT selection type for the section. The default is 5 (IMAGE_COMDAT_SELECT_ASSOCIATIVE) if the ASSOC= option is used, and 0 otherwise. This option is valid only for a COMDAT section.
The ASSOC=<section symbol> option causes the section being declared to be linked if the section identified by section_symbol is linked. Use of this option causes the COMDAT selection type to default to 5 (IMAGE_COMDAT_SELECT_ASSOCIATIVE). This option is valid only for a COMDAT section, and the target of the association (section symbol) must be a COMDAT section as well.
Examples:
SEL_NODUP .equ 1
.section .text{-foo},code,selection=SEL_NODUP
nop
.section .data{-bar},data,assoc=.text{-foo}
.data 0
.section .text{-`??main@A`},code,selection=SEL_NODUP
nop
.section .data{-`??main@Q`},data,assoc=.text{-`??main@A`}
.data 0
It is possible to redeclare (re-enter) a section that was previously declared in the same file. Figure 5.2 shows a simple example of section restart.
Note: When using the .SECTION assembler directive to restart a section, the second and third operands can be omitted. The original specifications when first declaring the section remain valid.
Figure 5.2 Section Restart
Use ALIGN = <boundary alignment value> to start a relative address section. The linkage editor will adjust the start address of the section to be a multiple of the boundary alignment value. The boundary alignment value specified must be an absolute value, and forward reference symbols must not appear in the specification. The values allowed for the boundary alignment value are powers of 2 <= 2^
5.2.2 .ORG: Location Counter Value Setting
Syntax:
.ORGD<location-counter-value>
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .ORG mnemonic in the operation field
· Operands: Enter the new value for the location counter in the operand field
Description: .ORG is an assembler directive that sets the value of the location counter within the current section. The .ORG assembler directive is used to place executable instructions or data at a specific address. The location counter value specified must be an absolute value, and forward reference symbols must not appear in the specification. The values allowed for the location counter value are from H'00000000 to H'FFFFFFFF (-2,147,483,648 to 4,294,967,295 in decimal). However, a practical limit is imposed by the size of available memory.
The .ORG assembler directive may not be used to set the location counter backward (e.g., to set the location counter to a value which is less its current value). When the .ORG assembler directive is used to set the location counter forward, the memory locations between the old location counter value and new location counter value are set to zero.
Coding Example:
.SECTION DT,DATA
.DATA.L H'11111111
.ORG H'00000F00 ; This statement sets the value of the location
; counter.
.DATA.L H'22222222 ; The integer data H'22222222 is stored at
; offset H'00000F00 within section DT.
Figure 5.3 shows this example in more detail.
Figure 5.3 Details of Location Counter Coding Example
Coding Example:
.SECTION .text
.DATA.L 0
; the location counter is now 4.
.ORG 0x100
; the location counter is now 0x100;
; locations from 0x4 to 0xFF (inclusive) are set to 0 (zero).
.DATA.L 0x100
; the location counter is now 0x104
.ORG 0x80 ; this directive is illegal!
; the previous line got an error message;
; the location counter is still 0x104.
5.2.3 .ALIGN: Location Counter Value Correction
Syntax:
.ALIGND<boundary alignment value>
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .ALIGN mnemonic in the operation field
· Operands: Enter the boundary alignment value in the operand field
Description: .ALIGN is an assembler directive that corrects the location-counter-value to be a multiple of the boundary alignment value. executable instructions and data can be allocated on specific boundary values (address multiples) by using the .ALIGN assembler directive.
The boundary alignment value specification must be an absolute value, and forward reference symbols must not appear in the specification. The values allowed for the boundary alignment value are powers of 2 <= 2
5.3 Symbol Handling Assembler Directives
5.3.1 .EQU: Symbol Value Setting (Resetting Not Allowed)
5.3.2 .ASSIGN: Symbol Value Setting (Resetting Allowed)
5.3.3 .REG: Alias of a Register Name Definition
The assembler provides the following symbol directives:
.EQU: sets a symbol value
.ASSIGN: sets and resets a symbol value
.REG: defines the alias of a register name
5.3.1 .EQU: Symbol Value Setting (Resetting not Allowed)
Syntax:
<symbol>[:]D.EQUD<symbol value>
Statement Elements:
· Label: Enter the symbol that is to be set a value in the label field
· Operation: Enter the .EQU mnemonic in the operation field
· Operands: Enter the value to be set to the symbol in the operand field
Description: .EQU is an assembler directive that sets a value to a symbol. Symbols defined with the .EQU directive cannot be redefined. Symbols defined with .EQU cannot be used as export or import symbols, and cannot be referenced from the debugger.
The symbol value specification may be an arbitrary expression, including address and relative values and forward reference symbols. However, there are constraints on expressions involving relative values. See 2.8.3, Notes on Expressions, for reference. The values allowed for the symbol value are from H'00000000 to H'FFFFFFFF (-2,147,483,648 to 4,294,967,295 in decimal).
Coding Example:
X1: .EQU 10 ; The value 10 is set to X1,
X2: .EQU 20 ; The value 20 is set to X2.
CMP/EQ #X1,R0 ; This is the same as CMP/EQ #10,R0.
BT LABEL1
CMP/EQ #X2,R0 ; This is the same as CMP/EQ #20,R0.
BT LABEL2
5.3.2 .ASSIGN: Symbol Value Setting (Resetting Allowed)
Syntax:
<symbol>[:]D.ASSIGND<symbol value>
Statement Elements:
· Label: Enter the symbol that is to be set a value in the label field
· Operation: Enter the .ASSIGN mnemonic in the operation field
· Operands: Enter the value to be set to the symbol in the operand field
Description: .ASSIGN is an assembler directive that sets a value to a symbol. Symbols defined with the .ASSIGN directive can be redefined with the .ASSIGN directive.
The symbol value specification must be an absolute value or an address value, and forward reference symbols must not appear in the specification. See section 2.8.1, Expression Elements for reference. The values allowed for the symbol value are from H'00000000 to H'FFFFFFFF (-2,147,483,648 to 4,294,967,295 in decimal).
Definitions with the .ASSIGN directive are valid from the point of the definition forward in the program. Symbols defined with .ASSIGN cannot be used as export or import symbols, and cannot be referenced from the debugger.
Coding Example:
X1: .ASSIGN 1
X2: .ASSIGN 2
CMP/EQ #X1,R0 ; This is the same as CMP/EQ #1,R0.
BT LABEL1
CMP/EQ #X2,R0 ; This is the same as CMP/EQ #2,R0.
BT LABEL2
X1: .ASSIGN 3
X2: .ASSIGN 4
CMP/EQ #X1,R0 ; This is the same as CMP/EQ #3,R0.
BT LABEL3
CMP/EQ #X2,R0 ; This is the same as CMP/EQ #4,R0.
BF LABEL4
5.3.3 .REG: Alias of a Register Name Definition
Syntax:
<symbol>[:]D.REGD <register name>
<symbol>[:]D.REGD(<register name>)
Statement Elements:
· Label: Enter the symbol to be defined as the alias of a register name in the label field
· Operation: Enter the .REG mnemonic in the operation field
· Operands: Enter the register name for which the alias of a register name is being defined in the operand field
Description: .REG is the assembler directive that defines the alias of a register name. The alias of a register name defined with .REG can be used in exactly the same manner as the original register name. The alias of a register name defined with .REG cannot be redefined. The alias of a register name can be defined for any register. See section 2.4 Reserved Words for reference. Definitions with the .REG directive are valid from the point of the definition forward in the program. Symbols defined with .REG cannot be used as export or import symbols, and cannot be referenced from the debugger.
Coding Example:
MIN: .REG R10
MAX: .REG (R11)
MOV #0,MIN ; This is the same as MOV #0,R10.
MOV #99,MAX ; This is the same as MOV #99, R11.
CMP/HS MIN,R1
BF LABEL
CMP/HS R1,MAX
BF LABEL

String constants in the .SDATA family of directives are allowed to be one or more of the following in any combination:
“quoted string”
<control char expression>
To simultaneously support this syntax and allow more complicated expressions, the assembler requires that parentheses be put around string constants (of the above form or otherwise) if they are to be used as part of more complicated expressions (for instance, string comparisons) in .SDATA and related directives. In all other contexts, string constants may only be “double quoted strings” and they may be used without parentheses.
Examples:
.data “abc” < “def” ; this is the same as .data 1
.sdata (“abc” < “def”) ? “yes” : “no”
; the previous line is a syntax error
.sdata ((“abc”) < (“def”)) ? “yes” : “no”
; the previous line is still a syntax error
.sdata ((“abc”) < (“def”)) ? (“yes”) : (“no”)
; the previous line is correct, and the same as .sdata “yes”
5.4.1 .COMMON: Data Reservation with Default Zero Initialization
Syntax:
.COMMOND<symbol name>[,<size>]
Statement Elements:
· Label: The label field is not used
· Operation: Enter .COMMON mnemonic in the operation field
· Operands: Enter the name of the common symbol to define, optionally followed by the number of bytes that the data occupies (defaults to zero)
Description: The .COMMON directive may be used to define a symbol that should be initialized to zero unless some other object file calls for it to be initialized to a specific value. This facility is necessary to support the equivalent of (and assemblable listing for) C code such as the following example, which in external (file) scope means that if no other file defines and initializes variable a, then a should be placed in the .bss section, which causes it to be initialized to 0.
C Coding Example:
int a;
If another file defines a, such as in the following example, then both files will refer to the same variable a, which will be initialized to 5, and no link error will result.
C Coding Example:
int a = 5;
Note: This works differently in C++; the C++ language requires that linking the above example would result in a link error.
Example:
.common _foo,4
.common _bar,2
.common __fltused
The preceding examples are equivalent to this C code:
int foo;
short bar;
void f (void)
{-
float a = 4.5; // force __fltused symbol
}

5.4.4 .SDATA: Character String Data Reservation
Syntax:
[<symbol>[:]]D.SDATAD<character string>[,<character string>...]
Statement Elements:
· Label: Enter a reference symbol in the label field if required
· Operation: Enter the .SDATA mnemonic in the operation field
· Operands: Enter the character string(s) to be reserved in the operand field
Description: .SDATA is the assembler directive that reserves character string data in memory. See section 2.9, Character Strings. A control character can be appended to a character string. The syntax for this notation is as follows:

The ASCII code for a control character specification must be an absolute value, and forward reference symbols must not appear in the specification.
Coding Example:
.ALIGN 4 ; This statement adjusts the value of the
; location counter.

; data.
.SDATA """BBB""" ; The character string in this example
; includes double quotation marks.
.SDATA "ABAB"<H'07> ; The character string in this example has a
; control character appended.

5.4.5 .SDATAB: Character String Data Blocks Reservation
Syntax:

Statement Elements:
· Label: Enter a reference symbol in the label field if required
· Operation: Enter the .SDATAB mnemonic in the operation field
· Operands: First operand: (block count) Enter the number of character strings as the first operand
Second operand: (character string) Enter the character string to be reserved as the second operand

.SDATAB 2,"""BBB""" ; The character string in this example

Description: .SDATAZB is the assembler directive that reserves the specified number of character strings (each with zero terminator) consecutively in memory. The block count specification must be an absolute value, and forward reference symbols must not appear in the specification. A value of 1 or larger must be specified as the block count. The maximum value of the block count depends on the length of the character string data. The length of the character string data multiplied by the block count must be less than or equal to H'FFFFFFFF (4,294,967,295 bytes).
A control character can be appended to a character string. The syntax for this notation is as follows:
<character string><<ASCII code for a control character>>
The ASCII code for a control character specification must be an absolute value, and forward reference symbols must not appear in the specification.

5.6 Function-Definition Assembler Directives
5.6.1 .ENTRY: Function Definition
5.6.2 .BIGENTRY: Function Definition (Large Functions)
5.6.3 .PROLOG: End of Function's Prolog Code
5.6.4 .ENDF: End of Function
5.6.5 .PDATA: Language Handler and/or Handler Data
5.6.6 Calling Convention Macros
5.6.7 Object Module Assembler Directives
5.6.8 .DEBUG: Symbolic Debug Information Output Control
5.6.9 .DEBUG: Symbolic Debug Information Output Control
To support the requirements of structured exception handling and provision of stack traces in the debugger, object files must contain information regarding where functions begin and end, and what part of each function is devoted to setting up the function’s stack frame. Programmers coding in assembly language provide this information using the following directives:
· .ENTRY: Defines a function and marks its beginning.
· .BIGENTRY: Defines a large function and marks its beginning.
· .PROLOG: Marks the end of the function prolog. The function prolog is the code at the beginning of the function that sets up the function’s stack frame, in accordance with the Calling Standard Specification.
· .ENDF: Marks the end of the function.
· .PDATA: Defines the language specific exception handler, and optionally data for that handler, for the following or current function.
Note: For more detailed information on prolog code and related topics, refer to the Calling Standard Specification document. This section is primarily concerned with the syntax and semantics of the relevant assembler directives. It is recommended that programmers use the calling convention macros described in the Calling Standard Specification, rather than directly using these directives.
5.6.1 .ENTRY: Function Definition
Syntax:
<symbol>[:]D.ENTRY
Statement Elements:
· Label: Enter a reference symbol in the label field; this is required
· Operation: Enter the .ENTRY mnemonic in the operation field
· Operands: The operand field is not used
Description: The .ENTRY directive marks the beginning of a function, and associates a name with that function. The .ENTRY (or .BIGENTRY) directive should be inserted before the first line of code (.DATA and related directives are fine). If the assembler encounters code before any .ENTRY (or after a .ENDF, with no intervening .ENTRY), a warning is issued and the assembler acts as though a .ENTRY directive had been found immediately before the line of code.
The label operates as a normal label (causing the symbol to be defined with the current value of the location counter as the value of the symbol). The label also associates the symbol with the function.
Refer to examples given in the PDATA directive section.
5.6.2 .BIGENTRY: Function Definition (Large Functions)
Syntax:
<symbol>[:]D.BIGENTRY
Statement Elements:
· Label: Enter a reference symbol in the label field; this is required
· Operation: Enter the .BIGENTRY mnemonic in the operation field
· Operands: The operand field is not used
Description: The .BIGENTRY directive marks the beginning of a large function, and associates a name with that function. The .BIGENTRY (or .ENTRY) directive should be inserted before the first line of code (.DATA and related directives are fine). If the assembler encounters code before any .ENTRY/.BIGENTRY (or after a .ENDF, with no intervening .ENTRY/.BIGENTRY), a warning is issued and the assembler acts as though a .ENTRY directive had been found immediately before the line of code.
The label operates as a normal label (causing the symbol to be defined with the current value of the location counter as the value of the symbol). The label also associates the symbol with the function. Refer to examples given in the following .PDATA directive section.
Ordinarily, the .ENTRY directive should be used. For functions more than 16,777,214 bytes long, or whose prolog is more than 510 bytes long, the .BIGENTRY directive should be used. If. ENTRY is used for a function that needs .BIGENTRY, the assembler will issue error 554 or 555. If .BIGENTRY is used for a function that could use .ENTRY, no warning or error will result, and the output will be correct. However, 8 bytes is wasted in the code section in which the .BIGENTRY directive appears.
Note: A function that requires the use of .BIGENTRY would be very unusual.
Refer to examples given in the .PDATA directive section.
5.6.3 .PROLOG: End of Function's Prolog Code
Syntax:
.PROLOG
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .PROLOG mnemonic in the operation field
· Operands: The operand field is not used
Description: The .PROLOG directive marks the end of the prolog code of a function. The prolog code is the code at the beginning of a function that sets up the stack frame for the function, in accordance with the Calling Standard Specification. This includes saving the PR register, pushing other registers onto the stack, setting up the frame pointer, etc. See the Calling Standard Specification for reference. The .PROLOG directive should appear between the last line of prolog code and the first line of non-prolog code for the function. If the function has no prolog code, then the .PROLOG directive should appear between the .ENTRY directive for the function and the first line of code in the function.
It is important that the .PROLOG directive be used appropriately, and that the prolog code (and the epilog code) of each function conform to the Calling Standard Specification. Otherwise, structured exception handling may not work correctly, and the debugger may be unable to provide stack traces. If the .PROLOG directive is not specified for a function (ie, an .ENDF directive is encountered without a .PROLOG directive having been encountered since the most recent .ENTRY directive), the assembler will issue a warning, and act as though the .PROLOG directive had been specified immediately following the .ENTRY directive. This effectively indicates that the function has no prolog code. If the function does in fact have prolog code, then structured exception handling and stack tracing may not operate properly. It is best to always use a .PROLOG directive, even if the function has no prolog code.
Coding Example:
Note: See also examples for the PDATA directive section.
fun6: .entry
; this is the prolog code:
mov.l r14,@-sp
mov.l r8,@-sp
sts.l pr,@-sp
mov sp,fp
add #12,fp
; end of prolog code.
.prolog ; mark end of prolog code
add #-16,sp
; function code goes here
mov fp,r2
add #-12,r2
lds.l @r2+,pr
mov.l @r2+,r8
mov r2,sp
rts
mov.l @sp+,fp
.endf
5.6.4 .ENDF: End of Function
Syntax:
.ENDF
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .ENDF mnemonic in the operation field
· Operands: The operand field is not used
Description: The .ENDF directive marks the end of a function, and should appear after the last line of code for each function. If a .ENDF directive is encountered when there is no matching .ENTRY directive (ie, if no .ENTRY directive has been encountered, or no .ENTRY directive has been encountered since the most recent .ENDF directive), the assembler issues an error message. If the end of the program (or section) is reached, and a function is still pending (either because there is a .ENTRY directive with no matching .ENDF directive, or because code was encountered without a .ENTRY directive, and so the assembler implicitly opened a function), the assembler issues a warning message and acts as though there were a .ENDF directive at the end of each section that has a pending function.
When the assembler encounters an .ENDF directive, it writes out any pending literal pool for the current section (as if a .pool directive had been encountered). It also takes any pending .PDATA directive information, applies it to the current function (the one being terminated by the .ENDF directive), and resets the .PDATA directive information.
Refer to examples given in the PDATA directive section.
5.6.5 .PDATA: Language Handler and/or Handler Data
Syntax:
.PDATAD<handler address>[,<handler data>]
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .PDATA mnemonic in the operation field
· Operands: Enter the address of the language specific handler, optionally followed by the address of the data to be used by the handler
Description: The .PDATA directive specifies a language specific exception handler for the following or current function. The .PDATA directive must appear before the .ENTRY or .BIGENTRY section to which it applies. The exception handler should be the address of a function, although no warning or error will be issued for a non-relative operand. The programmer may optionally also provide one longword (4 bytes) of data for use by the exception handler. Depending on the handler, that data may also be a pointer (an address). The handler address and handler data operands may be arbitrary expressions.
Forward references and relative values are permitted. The .PDATA directive is not persistent; it applies to no more than one function. To specify an exception handler (and optionally handler data) for more than one function, a .PDATA directive must be supplied for each such function. Also, function information (including information supplied by .PDATA directives) is maintained separately for each section. The .PDATA directive is optional. The assembler issues no error or warning messages if the .PDATA directive is not supplied.
Coding Examples:
.section .text
.import ex_handler
.import handler_data
; set up exception handler for following function (fun1 in
; this case).
.pdata ex_handler,handler_data
fun1: .entry
.prolog
rts
nop
.endf
; fun1 uses ex_handler & handler_data.
fun2: .entry
.prolog
rts
nop
.endf
; fun2 has no exception handler or handler data (both 0).
.pdata ex_handler
fun3: .entry
.prolog
rts
nop
.endf
; fun3 uses ex_handler; handler data is 0 (the default).
.pdata fun4,5
fun4: .entry
.prolog
rts
nop
.endf
; fun4 is its own exception handler (probably a bad idea);
; handler data is a constant 5.
fun5: .entry
.prolog
rts
nop
.endf
.pdata ex_handler
; fun5 has no exception handler or handler data; the .pdata
; directive above applies to the next function. (The assembler
; issues a warning if no function follows in the same section,
; since in that case the .pdata directive would have no effect.)
5.6.6 Calling Convention Macros
Calling Convention Macros: It is strongly recommended that programmers use the calling convention macros, rather than directly using the relevant assembler directives. These macros are documented in detail in Appendices A and D of the Calling Standard Specification, and their definitions are provided in the header file kxsh3.h, which may be used via the .INCLUDE directive.
Following is a brief overview of the macros:
START_REGION NameBegin
END_REGION NameEnd
Marks the beginning and end of a contiguous range of text or data. NameBegin labels the beginning of the range and NameEnd labels the end. Both names are in the global name space.
NESTED_ENTRY Name[,[Section=]SectionName]
Declares the beginning of a routine that either has an existing frame or creates a stack frame. Name is the routine name and is in the global name space. SectionName is the name of the section in which the entry will appear. SectionName is optional and defaults to .text. A NESTED_ENTRY must have an associated PROLOG_END and ENTRY_END.
LEAF_ENTRY Name[,[Section=]SectionName]
Declares the beginning of a routine that does not require any prolog code. Name is the routine name and is in the global name space. SectionName is the name of the section in which the entry will appear. SectionName is optional and defaults to .text. A LEAF_ENTRY must have an associated ENTRY_END. An explicit PROLOG_END is not needed in this case because LEAF_ENTRY includes PROLOG_END. Not all leaf routines can use LEAF_ENTRY.
ALTERNATE_ENTRY Name[,[Section=]SectionName]
Declares an alternate entry to a routine of either NESTED_ENTRY or LEAF_ENTRY type. Name is the entry point and is in the global name space. SectionName is the name of the section in which the entry will appear. This parameter is not used by the ALTERNATE_ENTRY macro, but is accepted and ignored for consistency with NESTED_ENTRY and LEAF_ENTRY. If used, an ALTERNATE_ENTRY call must appear in a routine's body.
ENTRY_END [Name]
Ends the current routine that was specified by a prior NESTED_ENTRY or LEAF_ENTRY. Name should be the same name used in the NESTED_ENTRY or LEAF_ENTRY macros. Name is currently ignored by the ENTRY_END macro.
EXCEPTION_HANDLER Handler
Associates the exception handler Handler with the subsequent NESTED_ENTRY or LEAF_ENTRY routine. This association is in effect until the matching ENTRY_END macro is encountered.
EXCEPTION_HANDLER_DATA Handler,HandlerData
Associates the exception handler Handler and the HandlerData with the subsequent NESTED_ENTRY or LEAF_ENTRY routine. This association is in effect until the matching ENTRY_END macro is encountered.
PROLOG_END
Marks the end of the prolog area. This must appear following a NESTED_ENTRY or LEAF_ENTRY macro, following the prolog area and prior to the matching ENTRY_END macro.
NESTED_BIGENTRY Name[,[Section=]SectionName]
The same as NESTED_ENTRY, except uses the .bigentry assembler directive instead of the .entry assembler directive. Use this for functions that are more than 16,777,214 bytes long, or whose prolog is more than 510 bytes long.
(Note: Such a function would be very unusual.)
LEAF_BIGENTRY Name[,[Section=]SectionName]
The same as LEAF_ENTRY, except uses the .bigentry assembler directive instead of the .entry assembler directive. Use this for functions that are more than 16,777,214 bytes long.
(Note: Such a function would be very unusual.)

Instead of:		Use the following:

.align 4
.global fun7

.prolog

nop
.endf
.section special,code
.align 4
.global fun8
.pdata ex_handler
fun8: .entry
sts.l pr,@-sp
.prolog
bsr fun7
nop
lds.l @sp+,pr
rts
nop
.endf		LEAF_ENTRY fun7
rts
nop
ENTRY_END
EXCEPTION_HANDLER ex_handler
NESTED_ENTRY fun8,Section=special

PROLOG_END

nop
lds.l @sp+,pr
rts
nop
ENTRY_END

5.7.5 .HEADING: Source Program Listing Header Setting
Syntax:
.HEADINGD[<expression> [,<expression>...]]
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .HEADING mnemonic in the operation field
· Operands: Enter the header for the source program listing in the operand field
Description: .HEADING is the assembler directive that sets the header for the source program listing. The .HEADING directive can have as operands zero or more expressions (including constants and symbols) whose values may be numbers or strings. If the .HEADING directive is used with no operands, it disables the current heading (if any). Otherwise, the results of the operands are concatenated, and the concatenated result is used as the new heading. If numeric symbols or expressions are used, they must evaluate to absolute values.
Examples:
.heading “Sample Program”
; the heading is now: Sample Program
.heading “Code for SH”, _M_SH, “ revision”, _M_SH_REV
; the heading is now: Code for SH3 revision 6
The .HEADING directive can be used any number of times in a given source program. The range of validity for a given use of the .HEADING directive is as follows:
· When the .HEADING directive is on the first line of a page, it is valid starting with that page
· When the .HEADING directive appears on the second or later line of a page, it is valid starting with the next page
See section 2.9, Character Strings.
Coding Example:
.HEADING """SAMPLE.SRC"" WRITTEN BY YAMADA"

5.8.1 .RADIX: Default Integer Constant Radix Setting
Syntax:
.RADIXD<radix specifier>
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .RADIX mnemonic in the operation field
· Operands: (radix specifier) This specifier sets the radix (base) for integer constants with no radix specification (Table 5.18)
Table 5.18 Radix Specifier Integer Constants
Radix Specifier		Radix of Integer Constants
B (or b)Binary
Q (or q)Octal
O (or o)Octal
D (or d) (default)Decimal
H (or h)Hexadecimal
X (or x)Hexadecimal
Description: .RADIX is the assembler directive that sets the radix (base) for integer constants with no radix specification. When there is no radix specification with the .RADIX directive in a program, integer constants with no radix specification are interpreted as decimal numbers. If hexadecimal (radix specifier H) is specified as the radix for integer constants with no radix specification, integer constants whose first digit is A through F must be prefixed with a 0 (zero). The assembler interprets expressions that begin with A through F to be symbols. Specifications with the .RADIX directive are valid from the point of specification forward in the program.
Coding Example:
.RADIX D
X: .EQU 100 ; This 100 is decimal.
.RADIX H
Y: .EQU 64 ; This 64 is hexadecimal.
.RADIX X
Z: .EQU 0F ; A zero is prefixed to this constant "0F"
; since it would be interpreted as a symbol if
; it were written as simply "F".

Statement Elements:
· Label: The label field is not used
· Operation: Enter the .END mnemonic in the operation field
· Operands: The operand field is not used
Description: .END is the assembler directive that declares the end of the source program. Assembly processing terminates at the point that the .END directive appears.
Coding Example:

; source program.
5.8.3 .WEAK: Define "Weak External" Symbol
Syntax:
.WEAKD<weak name>,<default name>[,<type>]
Statement Elements:
· Label: The label field is not used
· Operation: Enter the .WEAK mnemonic in the operation field
· Operands: Enter the name of the symbol to define weakly, followed by the name of the symbol to use as the definition if no other definition is found at link time, optionally followed by the weak external type
Description: The .WEAK directive may be used to define a “weak external” symbol. Weak externals are a mechanism for programs allowing flexibility at link time. A .WEAK directive such as:
.weak unlink,__unlink
indicates that when the program is linked, if the the symbol “unlink” is defined by any object file, then references to “unlink” are resolved to its definition normally. However, if the symbol “unlink” is not defined by any object file, then references to “unlink” are resolved to “__unlink” instead. (The symbol “__unlink” must be defined in exactly one of the object files, or an error will result.)
The optional type argument is an expression (whose value must be absolute) giving the type of weak external. If the value is zero or the third argument is omitted, the “alias” type of weak external is generated. This is generally desirable; the optional third argument would not normally be used.
Examples:
.weak foo,bar,1
NO_SEARCH .equ 1
SEARCH_LIB .equ 2
.weak ick,yuk,NO_SEARCH
.weak snap,crackle,SEARCH_LIB
If a symbol appears in the third argument position, and the symbol happens to be relative, the assembler will issue error 404. The error does not indicate that relative symbols or expressions cannot be used in a .WEAK directive, but that the third argument has to have an absolute value.
Note that the C and C++ compilers prepend a _ (an underscore) to each symbol name. Consequently, if unlink and __unlink were defined and referenced in assembly language, the .WEAK directive would be coded as shown in the first above example. If unlink and __unlink were defined and referenced in C code, the .WEAK directive would be coded as follows:
.weak _unlink,___unlink
