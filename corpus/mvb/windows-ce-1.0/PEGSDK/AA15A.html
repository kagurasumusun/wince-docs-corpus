Operating System Components

The core of the Microsoft Windows 95 operating system consists of three main libraries: User, Kernel, and GDI. These have been condensed into two libraries for Windows CE:

· The Kernel

· The Graphics, Windowing, and Events Subsystem (GWES).

The Windows CE Kernel

Like Windows 95 and Windows NT®, Windows CE is a 32-bit operating system. The kernel provides system services for managing threads, memory, and resources. It maximizes available memory by taking advantage of dynamic-link libraries (DLLs) that link your program with routines in the library at the time they are called. DLLs are written in reentrant code, allowing applications to simultaneously share common routines and minimize the amount of memory-resident code required to execute applications.

Because the Windows CE kernel can run routines in a reentrant mode, some of the user functions Windows 95 stores in a DLL have been integrated into the Windows CE kernel. Utilizing preemptive routines in effect makes the kernel function like a DLL. It can share common code among multiple threads, but skips the extra step of calling a library function to access a routine in the kernel.

The kernel was designed specifically for small, fast, hand-held devices. It supports only a single address space; however, it employs a scheme for protecting each process in that space. Applications that attempt to access memory outside of their allocated space are halted by the system. The system is limited to 32 processes, but the number of threads running in those processes is unlimited.

Preemptive Multitasking

Windows CE supports the multithreaded Win32 programming model. It is capable of managing multiple processes with the possibility of more than one thread of execution within each process. This gives you the advantage of scheduling processes to run at the same time. It also means that you have to be aware that you are sharing the machine's resources—such as memory and the screen—with other programs.

Scheduling

Windows CE incorporates preemptive priority-based scheduling. It gives the appearance of running programs simultaneously by allotting processing time in intervals to each thread. It runs one thread for a short time before switching to another.

Each thread is assigned a priority, and CPU time is allocated based on priority. Threads set to run at a higher priority are never preempted by threads at a lower priority. For example, CPU time will not be allotted to threads with a Normal priority until all threads at the Above Normal level have finished.

The Graphics, Windowing, and Events Subsystem
Windows CE combines the Win32 libraries User and GDI (Graphics Device Interface), into one component called the Graphics, Windowing, and Events Subsystem (GWES). The event manager and window manager are analogous to Win32 User, and the Win32 GDI is replaced with a smaller GDI more suitable for the HPC.
GDI
Many GDI functions available to Windows 95–based applications do not make sense for small hand-held computers, or place too much of a burden on the system’s limited resources. These functions have been excluded from the API function set supported by Windows CE. Following is a list of some of the common GDI functions that are not currently supported by Windows CE:
· Printing and the device contexts used to store attributes that govern how the GDI operates on printers are not supported.
· TrueType fonts are not supported. Windows CE supports only raster fonts. There are seven rasterized system fonts faces available in several sizes stored in ROM.
· Color and custom palettes are not supported. Colors are mapped to two-bit-per-pixel grayscale. The IDE provides a resource editor for creating bitmaps and icons with the grayscale palette.
· Coordinate space transformation functions, such as SetMapMode, GetMapMode, SetViewportExt, and SetWindowExt, are not supported.
· Metafiles are not supported; all pictorial information is stored as bitmaps.
· The system provides only limited support for bit block transfers (BitBlt).
· Windows CE does not support the concept of a current point, so MoveTo and LineTo functions are not available.
· Windows CE does not support cursors except for the spinning hourglass wait cursor. Applications cannot show active targets by changing the size or shape of the cursor.
Window Management
Windows CE supports most common Win32 User API functions; however, due to size constraints posed by the screen it is best to use the entire display for your application’s window. Windows CE can be moved around the screen but they cannot be resized by the user. It is possible to create smaller windows for applications such as a calculator that can be used while a portion of another window is displayed, but most application windows should always run full screen.
The Windows CE operating system is tailored for full-sized application windows. Following are some differences between Windows CE and the standard Windows API to accommodate full screen applications:
· No support for owned windows except dialog boxes.
· No nonclient messages are sent to applications.
· The client area is maximized by supporting command bars that are in the client area and controlled by the application.
· Microsoft Windows Multiple Document Interface (MDI) is not supported.
· Cascading menus and bitmap menus are not supported; however the system does support owner-drawn menus.
The operating system and the shell control how the nonclient area is drawn and managed.
The system supports a touch screen driver so the stylus can be used to simulate left button mouse clicks. The concept of right button mouse clicks is not supported. If your application needs to simulate right button mouse clicks, it should incorporate the ALT+tap convention.
More information about Windows CE programming conventions is covered in Microsoft Windows CE Interface Design Guidelines and The Windows Interface Guidelines for Software Design.
Event Handling
Like Windows 95, Windows CE is an event-driven operating system. Each message is passed in a message structure, MSG. The Windows CE MSG structure contains the same six fields as Windows 95 messages, with one exception: The pt field of the MSG structure is passed the coordinates of the last position touched on the screen, rather than the coordinates of the current cursor position.
Hooking messages is not supported. Allowing applications to hook messages could seriously degrade the performance of the device. Because Windows CE is such an intensive messaging operating system, sending messages across extra process contexts would be inefficient.
The Shell and Services
The Windows CE shell incorporates a number of controls that give the HPC user interface the distinctive look and feel of Windows 95. Because the controls are supported by libraries that are part of the shell, they are commonly available to all applications. The shell provides a familiar interface for accessing documents, launching applications, switching between tasks, browsing the file system, and performing other services.
The Windows CE Shell and Desktop.
The shell also supports a Notification API. The Notification API lets an application register its name and an event with the system. When the event occurs the kernel will automatically start the named application.
Common Controls
Like Microsoft Windows 95 controls, Windows CE common controls are designed to provide clear, simple, and meaningful information to the user, and a means for the user to furnish input to the system and applications as needed.
One of the challenges you’ll encounter designing visually appealing applications for Windows CE is the small landscape-oriented screen. To maximize the screen real estate available for applications (the client area), the operating system supports a new type of control, the command bar. A single command bar replaces the separate menu and tool bars found on Windows 95–based application windows. To learn more about working with command bars read Chapter 8, “Command Bars.”

Object Store APIs
The object store consists of three distinct components:
· The file system
· The registry
· Databases
All data in the object store is compressed by the operating system. All three components share the same heap in the system area. Windows CE supports three APIs for manipulating data in the object store.
The Windows CE File System
The Windows CE file system supports all of the common Win32 file manipulation functions. Functions to create files and directories, read and write to files, and retrieve file and directory information are exposed to Windows CE applications. However, the concept of a working directory is not supported. DLLs for all applications must be stored in the \Windows directory. To avoid collisions with DLLs for other applications, each DLL should have a long descriptive file name.
The Windows CE Registry
The Windows CE system registry is similar to Windows 95 and Windows NT registries. The registry for all applications including the applications bundled in ROM is stored in the object store. Every key uses up precious system area. Guidelines for creating registry keys that minimize memory requirements and improve access time are listed in Chapter 3, “Memory Management.”
The Windows CE Database API
Windows CE has a built in database manager. It supports databases with a single-level hierarchy; nested objects are not supported. Windows CE databases consist of any number of records containing one or more fields. Each field is of a specific type or property. Defined properties include integers, strings, FILETIME structures, and byte arrays. The database API allows applications to designate up to four fields as keys for sorting and searching through records.
Windows CE supports the creation and management of multiple databases. Each database and each record in the database is registered with the system and assigned an object identifier. The database API uses the object identifier to specify the record and database being manipulated.
For more information about creating and maintaining databases read Chapter 5, “The Object Store.”
Windows CE Remote API
The Windows CE Remote API (RAPI) gives applications running on the desktop PC (the RAPI client) the ability to make function calls on the HPC (the RAPI server). RAPI runs over Winsock and TCP/IP. These synchronous function calls behave much like their Windows CE Win32 counterparts. A list of these functions and an overview of their implementation is provided in Chapter 11, “Remote API Functions.”
Windows CE Communications
Windows CE provides some standard Win32 interfaces for communicating with other devices. The system supports APIs designed to:
· Communicate with the desktop PC through direct serial or dial-up LAN connections.
· Provide support for infrared communication using IrDA protocol.
· Provide standard communication with direct serial devices.
· Provide standard communication between modems.
To achieve the communication objectives above, Windows CE exposes four distinct APIs:
· A subset of WinSock version 1.1
· Remote Access Service (RAS) connection and management functions
· Win32 serial functions
· A subset of the Telephony API (TAPI)
Windows CE WinSock API
Windows CE supports most of the common WinSock functions except for the WSA functions implemented to accommodate Windows 3.1 single-threaded design. It exposes TCP/IP and IrDA through the WinSock API. The system supports several modes of IrDA including IrCOMM, IrLPT, and a proposed new standard IrSock.
RAS Functions
Windows CE supports the standard Win32 RAS functions; however it allows only one connection at a time. RAS functions can be implemented for direct serial connections or dial-up modem connections.
Win32 Serial API
Windows CE provides support for standard Win32 serial API functions. It exposes file handling capabilities for creating, reading, and writing files, as well as serial communication functions.
Windows CE TAPI
Windows CE supports TAPI version 1.5. It provides the basic functions, structures, and messages for establishing outgoing calls and controlling modems from the HPC.
