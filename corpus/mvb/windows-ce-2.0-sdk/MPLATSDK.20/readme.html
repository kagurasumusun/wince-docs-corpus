RECOMENDED INSTALLATION PROCEDURE

  • To ensure proper functionality of emulation you need to be running Windows NT 4.0. Emulation on Windows 95 is not supported.
  • Install Microsoft Visual C/C++ 5.0 or another C/C++ compiler.
  • Install the Windows CE Platform SDK.

 

The Windows CE Platform SDK is designed to provide tools for building applications for Windows CE version 2.0. The Windows CE Platform SDK does not include the cross-compilers needed for developing binaries that run on Windows CE devices. These compilers are included in the Windows CE Toolkit for Visual C/C++ 5.0 available from Microsoft, or in a C/C++ development environment that supports Windows CE. Several sample applications are included in this SDK. Refer to the Windows CE Sample Applications section of this file for more information about these sample applications. While every effort was made to allow you to use the development environment of your choice, the makefiles that accompany the included samples are Visual C/C++ 5.0 specific and will need to be altered if you are using a different development environment.

 

Desktop Emulation Environment

The Windows CE emulation environment requires the Microsoft VC/C++ 5.0 (or equivalent) compiler, linker and related desktop build tools. The emulation environment requires Windows NT 4.0 or greater. Although you can install the Windows CE Platform SDK on Windows 95, the Windows CE Emulation environments, along with the Remote Tools, are not supported on Windows 95.

 

The H/PC v2 Windows CE Emulation Environment allows developers to build and test Windows CE applications on their Windows NT Workstation as if they were running on an H/PC v2 device. This facilitates application development. The H/PC v2 Emulation environment consists of an emulated shell and object store. The object store is contained in a file on your hard disk called "HPC.OBS". The object store resides in "<target install directory>\wce\emul\HPC directory. The SDK setup creates this for you. The object store is managed by FILESYS.EXE. The object store contains the registry, databases, and files. The tree structure is identical to the real object store on an H/PC v2 device. All semantics are the same. For example, the root is "\" and there is no concept of "current directory".

 

For emulation, H/PC uses EXPLOREM.EXE as the shell The emulated shell gives you the look and feel of a real H/PC v2 device, and they contain most of the functionality. Running multiple emulation shells at the same time is not supported. FILESYS.EXE can be launched directly or indirectly. It runs as a background task, so you won't see a window or anything else to indicate that it is running. To launch it indirectly, just launch any of the shell executables mentioned above. It will detect if FILESYS.EXE is running and, if not, start it for you. FILESYS.EXE will continue to run until logoff. Should it be necessary to terminate FILESYS, call FILESYS with the -c flag. The FILESYS command line options are:

  

To start filesys:

Filesys /s [/wceplatform:hpc ]

To close filesys:

Filesys /c [/wceplatform:hpc]

 

The emulated shell executable can also be started directly or indirectly. It is a fixed window that can't be moved or minimized. To start the emulated shell indirectly, launch an application that you have built for emulation (see below for building for emulation). This is any application that links to COREDLL.LIB(DLL). COREDLL.DLL will detect if the shell is running and, if not, start it for you. FILESYS.EXE is started for you as necessary. If you want to run your application without shell emulation, give the command line switch /NOSHELL to your application. Shell APIs will not be available to emulation applications that are started without the shell.

 

Though every effort possible was made to emulate H/PC v2 as closely as possible, emulation relies on Windows NT and therefore certain minor differences are visible. This version of Emulation does not support display driver emulation.

 

Building for Emulation

The include environment variable must be set to <the install location>\wce\include\HPC. The environment batch file HPCENV.BAT sets up both the build and runtime environment for emulation applications. The lib environment variable must be <the install location>\wce\lib\wce200\HPC\x86em. The Platform SDK Setup does this automatically for you. If you are using Visual C/C++ then you will either need to add the Visual C/C++ Library directory to the lib environment variable, or you can run Visual C/C++'s VCVARS32.BAT before you compile and link you application.

 

Your application must have _WIN32_WCE_EMULATION defined before including <windows.h>. This value can be defined in the makefile, as it is with the existing samples, or it can be defined in the source code.

 

All DLLs built for emulation need to have the entry point set to _DllMainCRTStartup@12. This is done by passing the -entry:_DllMainCRTStartup@12 switch to the linker. Additionally, if the DLL has a main function, it must be called DllMain.

All executables built for emulation need to have the entry point set to WinMainCRTStartup. This is done by passing the -entry:WinMainCRTStartup switch to the linker. The sample makefiles illustrate how to do this.

If your application contains both an .EXE and a .DLL file then copy both to the object store and to your emulation directory. The Windows CE Toolkit for Visual C/C++ 5.0 does this for you. If you are using the Windows CE Platform SDK, then the following EMPFILE commands will accomplish this for you:

Empfile –c Path\myapp.exe wce:windows\myapp.exe

Empfile –c Path\mydll.dll wce:windows\mydll.dll

Where PATH is the fully qualified path to where your file resides. For example, if your file is located at c:\myproj\myapp.exe the correct command would be

Empfile –c c:\myproj\myapp.exe wce:windows\myapp.exe

If you are targeting H/PC v2, the files will be copied into the \Windows directory of the object store, as well as %wceemuldir%\hpc\windows, where %wceemuldir% is your installation path.

Similarly, to launch an application from the emulated shell, the application must reside in the object store.

 

To run for emulation, the proper environment batch file, HPCENV.BAT, MUST be run first. This file simply modifies the path. RESTENV.BAT is also provided so that the previous path can be restored.

 

When building applications for emulation, if you are using the Visual C/C++ development environment, then you will need to link with the following libraries:

 

Emulation Libraries: COREDLL.LIB, COMMCTRL.LIB, COMMDLGM.LIB

Additional Emulation Libraries (as necessary): OLE32M.LIB, OLEAUTM.LIB, UUID.LIB, ASFORM.LIB, MSGSTORE.LIB, ADDRSTOR.LIB, HTMLVIEW.LIB, WININETM.LIB, TOOLHELP.LIB, ASFUUID.LIB, CESHELL.LIB, LIBC.LIB, LIBCD.LIB, LIBCMT.LIB, LIBCMTD.LIB, MSVCRT.LIB, MSVCRTD.LIB, NDIS.LIB, NTCOMPAT.LIB, PCMCIA.LIB, WINSOCKM.LIB

 

Empfile should be run to copy your applications and data files to the object store. For example, to copy your application to the H/PC object store you would first copy it to the wce\emul\HPC\windows\ directory, and then synchronize your H/PC object store with the wce\emul\HPC directory tree using the following command: "empfile –WCEPlatform:HPC -s". EMPFILE.EXE can be found in the emul\bin directory. If your application calls LoadLibrary on any DLL, then that DLL has to be empfile'd into the appropriate place in the appropriate object store.

 

Possible EMPFILE commands and their usage are illustrated below. To see a list of Empfile options and command line examples run Empfile /?, and select a platform.

USAGE: EMPFILE [options]...

options:

-c SOURCE DEST ('put' or 'get' a file from object store)

-d FILE (delete a file on object store)

-e FILE (check to see if a file exists on object store)

-s (synchronize object store with wce\emul\PLATFORM\ tree)

-r MYAPP ARGS (run myapp.exe in the object store with arguments ARGS)

 

examples:

EMPFILE -s

(Synchronize wce\emul\PLATFORM\ tree with object store)

EMPFILE -c c:\test.exe wce:windows\test.exe

(Copy c:\test.exe to object store's Windows\ directory)

EMPFILE -c wce:test.exe c:\test.exe

(Copy test.exe from object store to c:\)

EMPFILE -e windows\text.exe

(verify that test.exe Exists in object store's Windows\ directory)

EMPFILE -d test.txt

(Delete test.txt from object store root directory)

EMPFILE -r test.exe -10

(Run test.exe from object store with parameter "-10")

 

Note: "PLATFORM" is the platform selected in the Emulation Settings dialog.

Wildcards (eg. '*.EXE') are not supported.

Specify the fully qualified path name for the Copy command.

 

When you run EMPFILE without specifying a platform EMPFILE will ask you to select a platform. 

If you are copying a file to or from the object store you can either copy the file to the platform directory, or you can specify the full path in the "srcfile" parameter of EMPFILE. For example, empfile copy windows\mydll.dll wce:Windows\MyDll.Dll –WCEPlatform:HPC -noshell will look for the source file in wce\emul\HPC\windows. If the file is not there, you will receive a "file not found error".

Tools You Should Know About

WM_HIBER.EXE is a tool included in the emulation object store for each platform. WM_HIBER allows the user to send WM_HIBERNATE messages to either all applications or the application of their choice. The user can launch it from the Run dialog, by double-clicking its icon in explorer, or by calling CreateProcess().

 

Running WM_HIBER.EXE places an icon in the Taskbar Tray. Double-clicking this icon brings up a dialog that allows the user to enter the window that they would like to send the WM_HIBERNATE message to. Alternatively, the user can select to broadcast it to all applications. Selecting all applications however, causes the WM_HIBERNATE message to be sent to all applications, not just applications currently under emulation.

 

REGSVRCE.EXE allows COM server dlls to be registered. REGSVRCE has the following command line options:

 

REGSVRCE [/u] [/s] DLLName

/u - Unregister the server

/s - silent operation

 

WM_HIBER.EXE has been placed in the object stores for your convenience, and REGSVRCE.EXE can be found in the <target install>\wce\emul\hpc\windows directory.

 

CEREGEDIT from the menu, or PREGEDIT.EXE from the command line, allows you to alter your device registry under emulation. This tool can be found on the menu. Press the ALT key ad then left mouse click to exit CEREGEDIT.

 If you disconnect the remote device while you're using the Remote Registry Editor, reconnect and refresh or restart the Remote Registry Editor.

 

A Control Panel applet is now provided that provides a way for you to select which object store to use. In selecting an object store, you're limited to selecting object stores residing in the wce\emul\<platform> directory.

 

WINDBG ( invoked from the start menu as Window Debugger ) is a device independent application for debugging your Windows CE applications. Due to the extreme flexibility that it provides with respect to comm ports, baud rates, device types, etc, it is not possible to ship it preconfigured for your application. Please consult the help menu in Windbg for information on how to configure windbg for use in your specific circumstances.

ActiveSync

ActiveSync is intended for software developers who want to develop a synchronization module to synchronize any data between a Windows CE device and a desktop PC running Windows 95 or Windows NT operating system. Once developed and installed on both the device and PC, Windows CE Services automatically utilizes the module to synchronize user-defined data between the device and the desktop PC. Windows CE Services also provides a user interface allowing the user to configure what synchronization module to use. One example of these modules is the Schedule+ synchronization that synchronizes Schedule+ data with various PIM applications on the device. Note, ActiveSync is not intended to be used in the emulation environment provided with the Windows CE Platform SDK. The ActiveSync components can be found in the \wce\samples\win32\sync directory.
Note, ActiveSync components from the Windows CE Platform SDK should not be redistributed, as they are already made available to users as Windows CE Services.

 

Notes

  • If you encounter difficulties with window ordering and navigating to your emulated application in the H/PC shell, you can use the buttons on the NT Taskbar or Alt-Tab, to navigate to the desired application.
  • The Control Panel for H/PC emulation can not be navigated to by double clicking on "My Handheld PC, and then Alt clicking on Control Panel. The Control Panel can be navigated to by following the H/PC menu options from the Start button.
  • If you exit the H/PC shell, and then immediately attempt to restart it, the attempt to restart will fail.
  • If an NDIS driver ever reports NO_RESOURCES from a send then the NDIS wrapper will not retry the operation. In the Windows CE implementation of NDIS, the SendResoucesAvailable flag in the NdisMSendResourcesAvailable function is not always set, resulting in sends not being retried.
  • Under emulation the value of the bitmap field bmWidthBytes returned by CreateDIBSection() is incorrect. The cause of this is because emulation uses NT’s GDI.
  • If the Microsoft Office Manager (MOM) is up and you are experiencing problems with emulation menus then set MOM's properties to Auto Hide.
  • ISVs using AppInstall will need to test with CEAPPMgr which is provided by Windows CE Services.
  • Under emulation, any edit control will not have vertical or horizontal scroll bars.
  • The Svcsample does not run on version 1.00 Windows CE devices. In order to run the Svcsample on the device, a dll is required to be registered using the Remote Registry Editor. The Remote Registry Editor shipped with the Windows CE Platform SDK does not support version 1 Windows CE devices.
  • In MFC samples built for emulation, the menus cannot be activated from the keyboard using the alt-letter keys. Once a menu has been activated, however, items within the menus are accessible using the keyboard.
  • Repeatedly calling EMPFILE, even with the NOSHELL flag specified, causes the emulation file system to start and stop. This is not recommended, but if you need to do this then you should start Emulation's H/PC Explorer and leave it running for the duration of these operations.
  • To build the NE2000 DDK sample driver for the SH3 platform, modify the common.mak file in the top of the \wce\samples\ddk directory. Specifically, the compiler define for Emulation ( -D_WIN32_WCE_EMULATION ) needs to be removed and the processor defines need to be changed to reflect the appropriate processor. As an example: for the SH3, the x86 ( -Dx86 -Di486 -D_X86_ ) platform defines need to be replaced with the SH3 defines ( -DSHx -DSH3 -D_SH3_ ). The library directory needs to be changed to the SH3 library by replacing, LIBSUBDIR = x86Em with LIBSUBDIR = wcesh. The CPU define needs to be changed from X86 to SH3 and the compiler and linker defines need to point to the appropriate compiler and linker.

Note: The Microsoft Windows CE Platform SDK does not contain a compiler or linker for the supported platforms. You must supply an appropriate Compiler and Linker, such as the Microsoft Windows CE Toolkit for Visual C/C++ 5.0.
  • When writing applications for Windows CE 1.0 it is necessary to use the PALETTEINDEX macro to choose colors for GDI operations. The RGB macro is not supported for Windows CE 1.0. When writing applications for Windows CE 2.0 it is necessary to use the RGB macro to choose colors for GDI operations. The PALETTEINDEX macro is not supported for Windows CE 2.0.
  • Running emulation applications from the NT Explorer or FileManager is not directly supported. If you wish to do so, you will need to modify your system or user PATH Environment variable from the System applet in the Control Panel. The path to the emulator's windows directory ( typically 'C:\Program Files\Windows CE Platform SDK\wce\emul\hpc\windows ', your install location may vary) will need to be added to your PATH. Microsoft does not recommend this method due to the potential for conflict with other emulation environments such as version 1 emulation. Use the "Emulation Environment For the HandHeld PC" menu item instead, and run the sample from the command line using the fully qualified name of the executable.
 

Application Installation

The Windows CE SDK uses cabinet (CAB) files as a self-contained setup package to install applications on a Windows CE platform. This allows installations from several sources, such as a desktop computer or a Website. The installation and removal of applications to and from the desktop is overseen by Application Manager. This section describes the methods and tools available for these processes.

CABWIZ.EXE needs a full path name to run properly.  For example:

c:\program files\windows ce platformsdk\support\appinst\bin\cabwiz

This was done so that CABWIZ does not pick up another MAKECAB.EXE that may be in the path.  MAKECAB.EXE and CABWIZ.DDF can also be copied to your individual project directories.

Because of the error codes returned, this tool can not be executed in the build process with NMAKE or Developer Studio.  For automated builds a batch file that executes CABWIZ.EXE and checks the error code will need to be created. 

Supporting v1 and v2 Devices

Below is sample pseudo code to write a single setup program able to use v1 or v2 installation methods. 

if "HKLM\Software\Microsoft\Windows\CurrentVersion\App Paths\CEAppMgr.EXE" registry key exists then

use v2 AppInstall

else if "HKLM\Software\Microsoft\Pegasus\InstalledDir" registry value exists then

use v1 PPCLoad

else

neither HPC Explorer nor Windows CE Services is installed - exit setup

endif

...

// late in setup, copy the files and install to device

if using v2 AppInstall then

copy .CAB and .INI files to desktop PC

launch CEAppMgr with full file/path of the .INI file

else

copy application's SH3 and MIPS binaries and .LOAD file to desktop PC

ask user to connect their device

get the connected-device processor type ("HKCU\Software\Microsoft\Pegasus\CPU" registry value)

call PPCLoad::Load_Init()

call PPCLoad::Load() with the CPU information, full file/path of the .LOAD file, etc.

call PPCLoad::Exit()

endif

 

Device Libs

The Windows CE Platform SDK includes the actual libraries needed to build applications for H/PC 2.0 devices. These libraries are separated by chip type and can be found in subdirectories under the <Target Install Directory>\wce\lib\WCE200 subdirectory. If you are building software for the device do not use the _WIN32_WCE_EMULATION flag. This flag should only be used for emulation.

 

 

Emulation Debugging Information

The Windows CE Platform SDK now provides a debugging window that can be turned on or off with a registry setting.

 

The registry key is as follows :

 

[HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows CE Platform SDK\Debug]

"OutputWindow"="None"

 

After you have installed the Platform SDK, this key 'OutputWindow' is set to its default value 'None'. If one decides to obtain any debug information, this value should be changed to either 'Debugger' or 'Console' (case insensitive). The setting 'Debugger' directs all debug information to the active debugger (IDE debugger or WinDBG), while the setting 'Console' directs all debug information to each individual console window of applications (including filesys, device, explorem) currently running under the emulation.

 

To print debugging information to this window, NKDbgPrintfW() must be called. NKDbgPrintfW() is prototyped in DBGPRINT.H.

 

APIs That Behave Differently Under Emulation

Windows CE Emulation relies on underlying NT functionality and therefore your application may be able to do more in emulation than it can on a Windows CE device. If you use an API parameter that is not defined in Windows CE, the result may be different on the device.
