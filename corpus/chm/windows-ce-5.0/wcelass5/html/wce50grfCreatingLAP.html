Creating a LAP

The password LAP that is available by default in Windows CE can be replaced by a customized LAP if you want to have an alternate mechanism to authenticate the user. The custom LAP will be called exclusively by LASS on behalf of applications that need to authenticate a user.

To create a LAP, you must create a DLL with the following entry points:

  • InitLAP (function)
  • DeinitLAP
  • VerifyUser
  • LAPCreateEnrollmentConfigDialog

InitLap is called before the LAP is ever used. The active LAP is loaded on startup, and will remain loaded until the active LAP is changed.

DeinitLAP is called prior to unloading the LAP. No more calls can be made to this particular LAP after this point.

The application's call to VerifyUser is passed on to the LAP if the AE policy requires it. When it receives this call, the LAP should validate the user. Note that if the flag VU_NO_UI is set, the LAP must not display UI.

LAPCreateEnrollmentConfigDialog is called by the LASS UI. The LAP can choose to perform its enrollment in this dialog, or it can redirect the user to perform their enrollment elsewhere.

LASSReloadConfig must be called or the device must be rebooted for changes to take effect.

LAP Implementation Issues

  • Often LAPs require a fallback mechanisim. For example in the case of a Fingerprint LAP, there is often an ability to enter a strong password if the fingerprint recognition engine fails. Such mechanisms are LAP-dependant, and must be implemented in the LAP itself.
  • When you implement a LAP, it is important to consider what the behavior should be when VerifyUser is called before the user has been enrolled. The two recommended behaviors are:
    • VerifyUser returns TRUE until the user enrolls
    • Enrollment is forced on the first call to VerifyUser

    The password LAP, that is available in Windows CE, implements the first option, so it returns TRUE on a call to VerifyUser if the user has not enrolled.
