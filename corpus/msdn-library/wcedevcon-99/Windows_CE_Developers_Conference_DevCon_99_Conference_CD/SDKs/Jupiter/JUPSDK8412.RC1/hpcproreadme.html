Recommended Installation Procedure

The following list describes the steps you should go through to successfully install the Windows CE Platform SDK (H/PC Pro Edition 3.0).

  1. Install Windows NT 4.0 including at least Service Pack 3.
  2. Install Microsoft Visual C/C++ 6.0, Visual Basic 6.0, or other language compiler.
  3. Install Windows CE Platform SDK (H/PC Pro Edition 3.0).

To ensure proper functionality of emulation you need to be running Windows NT 4.0. Emulation on Windows 95/98 is not supported.

Windows CE Platform SDK (H/PC Pro Edition 3.0) is designed to provide tools for building applications for Windows CE version 2.11. Windows CE Platform SDK (H/PC Pro Edition 3.0) does not include the cross-compilers needed for developing binaries that run on Windows CE devices. These compilers are included in the Windows CE Toolkit for Visual C/C++ 6.0 and the Windows CE Toolkit for Visual Basic 6.0 available from Microsoft, or in a C/C++ development environment that supports Windows CE. Several sample applications are included in this SDK. Refer to the Windows CE Sample Applications section of this file for more information about these sample applications. While every effort was made to allow you to use the development environment of your choice, the makefiles that accompany the included samples are Visual C/C++ 6.0 specific and will need to be altered if you are using a different development environment.

The Handheld PC Edition 2.0 and Palm Size PC Edition 1.0 Platform SDK's are not compatible with the Handheld PC Pro Edition 3.0 Platform SDK and should be uninstalled prior to installing the H/PC Pro Edition 3.0 Platform SDK. The H/PC Pro Edition 3.0 Platform SDK is, however, compatible with the H/PC Edition 2.0 and PSPC Edition 1.0 Platform SDK Service Packs.

Desktop Emulation Environment

The Windows CE emulation environment requires the Microsoft VC/C++ 6.0 (or equivalent) compiler, linker and related desktop build tools. The emulation environment requires Windows NT 4.0 or greater. Although you can install Windows CE Platform SDK (H/PC Pro Edition 3.0) on Windows 95/98, the Windows CE Emulation environments, along with the Remote Tools, are not supported on Windows 95/98.

The H/PC Pro Edition 3.0 Windows CE Emulation Environment allows developers to build and test Windows CE applications on their Windows NT Workstation as if they were running on an H/PC 2.11 device. This facilitates application development. The H/PC Pro Edition 3.0 Emulation environment consists of an emulated shell and object store. The object store is contained in a file on your hard disk called "HPCPRO.OBS". The object store resides in " <target install directory>\Windows CE Tools\WCE211\MS HPC Pro\Emulation\hpcpro directory. The SDK setup creates this for you. The object store is managed by FILESYS.EXE. The object store contains the registry, databases, and files. The tree structure is identical to the real object store on an H/PC 2.11 device. All semantics are the same. For example, the root is "\" and there is no concept of "current directory".

For emulation, H/PC Pro Edition 3.0 uses EXPLOREJ.EXE as the shell. The emulated shell gives you the look and feel of a real H/PC 2.11 device, and it contains most of the functionality. Running multiple emulation shells at the same time is not supported. FILESYS.EXE can be launched directly or indirectly. It runs as a background task, so you won't see a window or anything else to indicate that it is running. To launch it indirectly, just launch any of the shell executables mentioned above. It will detect if FILESYS.EXE is running and, if not, start it for you. FILESYS.EXE will continue to run until logoff. Should it be necessary to terminate FILESYS, call FILESYS with the -c flag. The FILESYS command line options are:

To start filesys:

Filesys /s /wceplatform:hpcpro

To close filesys:

Filesys /c /wceplatform:hpcpro

The emulated shell executable can also be started directly or indirectly. It is a fixed window that can't be moved or minimized. To start the emulated shell indirectly, launch an application that you have built for emulation (see below for building for emulation). This is any application that links to COREDLL.LIB(DLL). COREDLL.DLL will detect if the shell is running and, if not, start it for you. FILESYS.EXE is started for you as necessary. If you want to run your application without shell emulation, give the command line switch /NOSHELL to your application. Shell APIs will not be available to emulation applications that are started without the shell. To start the emulated shell directly, use the "Start\Programs\Windows CE Platform SDK (HPC Pro)\Desktop Handheld PC Pro Emulation" shortcut from the desktop, or run EXPLOREJ.EXE from an Emulation Environment Window.

Though every effort possible was made to emulate H/PC 2.11 as closely as possible, emulation relies on Windows NT and therefore certain minor differences are visible. This version of Emulation does not support display driver emulation.

Building for Emulation

The include environment variable must be set to <the install location> \Windows CE Tools\WCE211\MS HPC Pro\Include. The lib environment variable must be <the install location> \Windows CE Tools\WCE211\MS HPC Pro\LIB\x86em. The environment batch file HPCPROENV.BAT sets up both the build and runtime environment for emulation applications. The Platform SDK Setup provides an "Emulation Environment for HPC Pro" shortcut for running HPCPROENV.BAT (located under the PROGRAMS menu, in Windows CE Platform SDK (HPC Pro)). If you are using Visual C/C++ then you will either need to add the Visual C/C++ Library directory to the lib environment variable, or you can run Visual C/C++'s VCVARS32.BAT before you compile and link your application.

Your application must have _WIN32_WCE_EMULATION defined before including <windows.h>. This value can be defined in the makefile, as it is with the existing samples, or it can be defined in the source code.

All DLLs built for emulation need to have the entry point set to _DllMainCRTStartup@12. This is done by passing the -entry:_DllMainCRTStartup@12 switch to the linker. Additionally, if the DLL has a main function, it must be called DllMain.

All executables built for emulation need to have the entry point set to WinMainCRTStartup. This is done by passing the -entry:WinMainCRTStartup switch to the linker. The sample makefiles illustrate how to do this.

If your application contains both an .EXE and a .DLL file then copy both to the object store and to your emulation directory. The Windows CE Toolkit for Visual C/C++ 6.0 does this for you. If you are using the Windows CE Platform SDK (H/PC Pro Edition 3.0), then the following EMPFILE commands will accomplish this for you:

Empfile –c "%Path%\myapp.exe wce:\windows"

Empfile –c "%Path%\mydll.dll wce:\windows"

If you are targeting H/PC 2.11, the files will be copied into the \Windows directory of the object store, as well as %HPCProEmulDir%\hpcpro\windows, where %HPCProEmulDir% is your emulation path.

Possible EMPFILE commands and their usage are illustrated below. To see a list of Empfile options from the command line run Empfile /?.

USAGE: EMPFILE [options]...

options:

-c src_filespec dst_filespec (Copy a file to or from the object store)

-d wce_filespec (Delete a file in the object store)

-e wce_filespec (Check existence of file in the object store)

-r wce_filespec ARGS (Run an application in the object store with arguments ARGS)

Where wce_filespec is of the form:

wce:\wce_path (e.g. wce:\myfile.txt)

When copying files, either src_filespec or dst_filespec must be a

wce_filespec. The dst_filespec must be a path to desktop or emulation.

Wild cards are allowed for src_filespec only if it is not a wce_filespec.

examples:

EMPFILE -c c:\test.exe wce:\windows

(Copy c:\test.exe to the HPCPRO object store's \Windows directory)

EMPFILE -d wce:\test.txt

(Delete test.txt from the HPCPRO object store's root directory)

EMPFILE -e wce:windows\text.exe

(Verify that test.exe exists in the HPCPRO object store's \Windows directory)

EMPFILE -r wce:\windows\test.exe -10

(Run test.exe from the HPCPRO object store's \Windows directory with parameter "-10")

Similarly, to launch an application from the emulated shell, the application must reside in the object store.

To run for emulation, the proper environment batch file, HPCPROENV.BAT, MUST be run first. This file simply modifies the path. RESTENV.BAT is also provided so that the previous path can be restored.

When building applications for emulation, if you are using the Visual C/C++ development environment, you will need to link with the following libraries:

Emulation Libraries: CORELIBC.LIB, COREDLL.LIB, COMMCTRL.LIB

Additional Emulation Libraries (as necessary): ADDRSTOR.LIB, ASFORM.LIB, ASFUUID.LIB, CESHELL.LIB, COMMDLG.LIB, HTMLVIEW.LIB, IMGDECMP.LIB, INKX.LIB, MLANG.LIB, MSGSTORE.LIB, NTCOMPAT.LIB, OLE32.LIB, OLEAUT.LIB, RICHINK.LIB, TNEFUTIL.LIB, TOOLHELP.LIB, UUID.LIB, WEBVIEW.LIB, WININET.LIB, WINSOCK.LIB

Tools You Should Know About

WM_HIBER.EXE is a tool included in the emulation object store for each platform. WM_HIBER allows the user to send WM_HIBERNATE messages to either all applications or the application of their choice. The user can launch it from the Run dialog, by double-clicking its icon in explorer, or by calling CreateProcess().

Running WM_HIBER.EXE places an icon in the Taskbar Tray. Double-clicking this icon brings up a dialog that allows the user to enter the window that they would like to send the WM_HIBERNATE message to. Alternatively, the user can select to broadcast it to all applications. Selecting all applications however, causes the WM_HIBERNATE message to be sent to all emulation applications.

REGSVRCE.EXE allows COM server dlls to be registered. REGSVRCE has the following command line options:

REGSVRCE [/u] [/s] DLLName

/u - Unregister the server

/s - silent operation

WM_HIBER.EXE and REGSVRCE.EXE have been placed in the object stores for your convenience.

CEREGEDIT allows you to alter your device registry under emulation. If the Windows CE Toolkit for Visual C/C++ 6.0 is installed, this tool can be found on the PROGRAMS menu under "Microsoft Visual Studio 6.0\Windows CE Tools\Remote Registry Editor".

If you disconnect the remote device while you're using the Remote Registry Editor, reconnect and refresh or restart the Remote Registry Editor.

A Control Panel applet is now furnished that provides a way for you to select which object store to use. In selecting an object store, you're limited to selecting object stores residing in the Window CE Tools\WCE211\MS HPC Pro\emulation\hpcpro directory.

Application Installation

The Windows CE SDK uses cabinet (CAB) files as a self-contained setup package to install applications on a Windows CE platform. This allows installations from several sources, such as a desktop computer or a Website. The installation and removal of applications to and from the desktop is overseen by Application Manager. This section describes the methods and tools available for these processes.

Note Windows CE no longer supports the AppInstall application.

CABWIZ.EXE needs a full path name to run properly. For example:

c:\Windows CE Tools\WCE211\MS HPC PRO\support\appinst\bin\cabwiz

This was done so that CABWIZ does not pick up another MAKECAB.EXE that may be in the path. MAKECAB.EXE and CABWIZ.DDF can also be copied to your individual project directories.

Because of the error codes returned, this tool can not be executed in the build process with NMAKE or Developer Studio. For automated builds a batch file that executes CABWIZ.EXE and checks the error code will need to be created.

Device Libs

Windows CE Platform SDK (H/PC Pro Edition 3.0) includes the actual libraries needed to build applications for H/PC 2.11 devices. These libraries are separated by chip type and can be found in subdirectories under the <Target Install Directory>\wce211\ms hpc pro\lib\. If you are building software for the device do not use the _WIN32_WCE_EMULATION flag. This flag should only be used for emulation.

Emulation Debugging Information

Windows CE Platform SDK (H/PC Pro Edition 3.0) now provides a debugging window that can be turned on or off with a registry setting.

The registry key is as follows :

[HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows CE Platform SDK\Debug]

"OutputWindow"="None"

After you have installed the Platform SDK, this key 'OutputWindow' is set to its default value 'None'. If one decides to obtain any debug information, this value should be changed to either 'Debugger' or 'Console' (case insensitive). The setting 'Debugger' directs all debug information to the active debugger (IDE debugger), while the setting 'Console' directs all debug information to each individual console window of applications (including filesys, device, explorem) currently running under the emulation.

To print debugging information to this window, NKDbgPrintfW() must be called. NKDbgPrintfW() is prototyped in DBGAPI.H.

Known Problems

If you encounter difficulties with window ordering and navigating to your emulated application in the H/PC Pro Edition 3.0 shell, you can use the buttons on the NT Taskbar or Alt-Tab, to navigate to the desired application.

If the Microsoft Office Manager (MOM) is up and you are experiencing problems with emulation menus then set MOM's properties to Auto Hide.

The Svcsampl sample is not supported under emulation. This sample is provided for use on actual hardware.

In some MFC samples built for emulation, the menus cannot be activated from the keyboard using the alt-letter keys. Once a menu has been activated, however, items within the menus are accessible using the keyboard or mouse.

When writing applications for Windows CE 2.11 it is necessary to use the RGB macro to choose colors for GDI operations. The PALETTEINDEX macro is not supported for Windows CE 2.11.

Running emulation applications from the NT Explorer or FileManager is not directly supported. If you wish to do so, you will need to modify your system or user PATH Environment variable from the System applet in the Control Panel. The path to the emulator's windows directory ( typically 'C:\Windows CE Tools\wce211\ms hpc pro\emulation\hpcpro\windows', your install location may vary) will need to be added to your PATH. Microsoft does not recommend this method due to the potential for conflict with other emulation environments. Use the "Emulation Environment for the HPC Pro" menu item instead, and run the sample from the command line using the fully qualified name of the executable.

IrDA is not supported in this version of emulation.

Before installing a new version of the SDK, make sure to uninstall the previous version of the SDK. You do not need to remove the previous SDK if you are installing the new version of the SDK in the same location.

The information stored in the lParam of a WM_CREATE message may not match with the values that were initially specified in the call to CreateWindow( ... ). This is because the Window NT and Window CE window managers use style bits slightly differently.

In order to use platform manager for H/PC Pro emulation it is necessary to install the TCP/IP protocol stack.

The Windows CE Security API's are not supported under Emulation.

This version of emulation does not support printing (or print-related APIs).

Windows CE emulation uses information from Windows NT in some situations. For example, the Fontcount property in Visual Basic for Windows CE will return the same value as the Fontcount property in Visual Basic for Windows - 32 bit edition.

The Desktop Size control panel applet allows developers to change the size of their Handheld PC Emulation desktop. This functionality is intended to help the developer test how her application would look on a Handheld PC of a size other than the default provided. To run this applet, launch the control panel and double-click the Desktop Size icon. Choose the desired new size of the desktop and press OK. For the new settings to take effect, suspend and re-launch emulation.

The Object Store control panel applet allows a developer to change which object store file emulation will use. It is useful if the developer wants to save off the object store in a known state and return to it later. Note that the object store contains all emulated files, directories, registry entries, and databases. Before using this applet, copy the object store you want to save to the hpcpro\windows\ directory with the extension ".obs" (e.g. hpcpro\windows\test.obs) when Handheld PC Emulation is not running. To switch to using this new copy of the object store, launch the Object Store applet from Emulation's control panel. Either type in the name of the new object store or select the Browse button to find it. Shut down and restart emulation for your change to take effect.

While possible, it is unadvised to rename the system folders in emulation, as doing so may cause problems for the emulator.

It is recommended that you exit all applications running under emulation before suspending (i.e., shutting off) the emulator.

Emulation does not allow you to modify hardware related settings like repeat rate and power savings settings.

The Windows CE task manager is not available under emulation. Because emulated CE applications are in reality NT processes, you must utilize the NT task manager for switching between emulated applications.

Running the emulator with the same screen resolution as the desktop resolution is sub-optimal. This situation can create conflicts between the emulation taskbar and the desktop taskbar.

While you cannot set the systemwide NT cursor, you can still use the cursor APIs in emulation.

Before including the icmpapi.h header file in your C/C++ code, you must include the ipexport.h file.

Copying multiple files to the emulated object store (i.e. using a batch file) may cause EMPFILE.EXE to hang. To avoid this problem, place a delay between successive EMPFILE.EXE calls.

Visual C/C++ 6.0 should be closed prior to installing the Platform SDK (H/PC Pro Edition 3.0).

Because emulation is based on the underlying Win32 API's running on Windows NT, the bmWidthBytes structure used by the CreateDIBSection function may return values that are consistent with Windows NT and not consistent with Windows CE.

APIs That Behave Differently Under Emulation

Windows CE Emulation relies on underlying NT functionality and therefore your application may perform differently in emulation than it can on a Windows CE device. If you use an API parameter that is not defined in Windows CE, the result may be different on the device. Be sure to test your applications on a Windows CE device. The following section describes known functions that behave differently under emulation.

Because the CE Emulation GDI functions do not SetLastError() when there is an error, GetLastError() does not work under emulation.

When attempting to use CreateBitmap() to create bitmaps with 2, 4 or 8 bits per pixel, a monochrome bitmap will always be returned.

The coordinates from the following functions are treated differently in emulation than they are when running on a CE device:

  • ClientToScreen();
  • ScreenToClient();
  • MoveWindow();

Because Handheld PC Pro emulation uses the NT gdi, the emulator does not support 2 bit per pixel (4 color) bitmaps. Therefore, the CreateDIBSection function will not succeed in emulation if the passed-in bitmap header information includes biBitCount of 2 or biClrUsed of 4. Use a larger palette for bitmaps in Handheld PC Pro emulation.

GlobalMemoryStatus: there is no distinction between CE memory and NT memory. Therefore, GlobalMemoryStatus returns info relevant to the system as a whole.

CeRunAppAtTime is not supported for emulation.

It is important to properly define function pointers that will be used to access CE API's in order to avoid conflicts in calling convention. Use the function prototypes in the SDK headers to determine the correct definition for application function pointers.

Debugging Control Applets in Windows CE

Windows CE classifies control panel applets as dynamic link libraries (DLLs).

    To debug these files on Windows CE with Developer Studio

  1. Create an .exe file that loads a particular .cpl.

    You can also use this technique with any other .dll file.

  2. Under Project->Settings->Debug, set the "Executable for debug session" and "Remote executable path and file name" edit boxes the name of the .exe file.
  3. Set the "Additional Dll's" parameter to specify the .cpl or .dll you wish to load.

Using IMAP4 Mail Service Under Emulation

Emulation for Windows CE Handheld PC Professional supports using the IMAP4 mail service. However, there is a known problem with configuring the IMAP4 mail service. After adding the IMAP4 mail service, it is necessary to connect to IMAP4 in order to start the mail service. From the Inbox application, select Connect from the Services menu to connect to the IMAP4 mail service. A message box will appear with the following message:

Your mail service is configurated to connect to Network Connection but there is no way to connect.
Please insert a modem or network card and try again.

If you select OK from this dialog, Inbox connects to the IMAP4 mail service even though the message box makes it appear as if the connection fails.

Implementing Registry-Based Notification

In registry-based notification, an application places a command line in the desktop system registry in one of two keys. When the event specified by the key occurs, the command line is executed. Registry-based notification is appropriate for applications that do not need some control of the connection manager nor the ability to register and unregister for connection notifications.

The keys used in registry-based notification are HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows CE Services\AutoStartOnConnect and AutoStartOnDisconnect. When a Windows CE-based device is connected to a desktop computer, the command line under AutoStartOnConnect is executed. Likewise, when the device is disconnected, the command line under AutoStartOnDisconnect is executed.

    To register an application for automatic execution

  1. Construct a named value that uniquely identifies the application.

    The named value should include a company and product name, such as MicrosoftHPCExplorerAutoConnect.

  2. Enter the named value under the appropriate key, either AutoStartOnConnect or AutoStartOnDisconnect.
  3. Define the named value as the application that is to be executed, including command line arguments.

Note The application file path must be wrapped with double quotes if arguments are provided.

The following registry editor (.reg) file shows how to register a command line for both AutoStartOnConnect and AutoStartOnDisconnect. In this example, when the Windows CE-based device is connected, Notepad.exe is started with a command line argument of c:\config.sys. When the device is disconnected, Notepad.exe is started with a command line argument of c:\autoexec.bat.

REGEDIT4
[HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows CE Services\AutoStartOnConnect]
"MicrosoftAutoConnectSample"="\"notepad\" c:\\config.sys"
[HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows CE Services\AutoStartOnDisconnect]
"MicrosoftAutoDisconnectSample"="\"notepad\" c:\\autoexec.bat"
