Introduction

With faster Pentium processors and operating systems such as Windows NT, Windows 95 and SCO UNIX Open Server 5 there is a need for faster bus adapters. PCI solves this problem by alleviating the "bottle necks" of older bus types. This document will explain how PCI functions and how it works with Plug and Play systems. What is PCI and how does it effect performance?

The PCI bus allows for high speed data transfer, almost reaching that of host processors. The standard PCI bus allows for 32 bit high speed data transfer at 33 MHz..   The bottle neck of data transfer in earlier ISA and EISA bus systems was the bus. The 8.33 MHz ISA bus requires, at minimum, two bus clock signals to transfer data if it's dealing with a zero wait state device.  The data path of the ISA system is 16 bits.   This 16 bit data path allows a maximum of two bytes to be transferred every two clock cycles which results in a maximum transfer rate of 8.33 Mbytes per second (theoretically). In an EISA System the BUS is still limited to 8.33 MHz but it uses only one clock cycle to perform a data transfer. The EISA BUS data path is 32 bits wide and allows a maximum of four bytes to be transferred every clock cycle.  This gives it a maximum transfer rate of 33 Mbytes per second (theoretically). If these were the only factors contributing to data throughput the maximum data transfer rates would have already been reached. There are however, other variables that must be added into this equation. The first issue being the CPU which must intervene to transfer data from the card to the memory (adapter to host transfer). The second issue is that the ISA bus does not support burst mode. Other lesser trouble spots can be the software drivers and the protocols bound to the logical board as well as slow disk I/O and poor data management. All of the above will reduce performance, thus reducing throughput on the network.

The Origins of PCI

PCI origins began with local bus. Prior to implementing the PCI host controller the devices were attached directly to the system's local bus by either using the direct or the buffered connection. The direct connection proved to have some problems in that only one device could be attached to the bus and there was difficulty in design due to the high frequencies generated on the bus. The answer to this was a buffered connection. The buffered connection allowed for multiple local bus devices to be attached simultaneously.   This method also reduced the load to the processor by isolating the buffered local bus. Although this approach was an improvement, it still had some drawbacks including problems with bus-mastering adapters. If a bus- mastering adapter is performing an operation, the CPU is paused until the bus mastering card has released the bus. The last type uses a host bus controller chip between the CPU local bus and the main memory. This controller chip integrates the L2 cache controller and a bridge to the CPU, main memory and an I/O bus (PCI bus). Using this last approach allows the system to take advantages of the PCI Bus architecture.

PCI Specification

Plug and Play and the PCI specification started from two completely different origins. However, the PCI architecture and model fit perfectly into the PnP model which allowed the two architectures to merge. The major difference is that the PnP BIOS must configure the PCI adapter. It cannot be solely configured by the PnP operating system.

PCI can has gone through a few revisions since it was first introduced by INTEL on June 6, 1992. Version 1.0 had some problems. Many of the shortcomings were corrected with the introduction of Rev. 2.0 in April of 1993.  In the first quarter of 1995 the Rev. 2.1 was introduced with improvements over the previous revisions. A few of the improvements are:

1. Processor Independence

Components that are designed for PCI are PCI and not processor specific. This is useful in not having to design for future processors.

2. Bus Speed

The PCI Rev. 2.0 supports up to 33MHz bus speeds. The 2.1 supports up to 66 MHz.

3. Automatic Configuration

This standard supports the full bit level specification of the configuration registers in order to support automatic adapter / peripheral detection and configuration.

4. Transaction Integrity Check

Parity Checking on Address, Command and Data lines.

5. Bus Master Support

Full Support of PCI Bus support allowing peer-to-peer PCI bus access, as well as main memory and expansion bus devices through PCI and expansion bridges. Also, a PCI master can access a target that resides on another PCI bus lower in the bus architecture.

6. 64 Bit Bus Width

Full definition of a 64 bit extension.

 

PCI System configuration

Configuration of PCI Devices is handled completely by the system BIOS.  The BIOS uses addressing schemes that will not conflict with existing ISA or EISA addresses. The PCI Bus uses bridges, as seen in Fig 2, which shows an ISA bridge off of the PCI bus. Bridges allow for the use of other bus architectures to be used in the same system. A PCI bus can bridge ISA, EISA, CARD BUS and second PCI Busses. If an ISA bus is used the I/O addressing will be the same as on a non PCI machine, with valid addresses ranging from 100 to 3FF. If an EISA bus is implemented the range will be the same as any other EISA machine, where the first EISA slot will be set to 0x1000, the second to 0x2000 and so forth. For the first PCI I/O address it will search for the highest available address used by another bus type and place it’s address beyond that. For example if the machine had four EISA slots the first available address for the PCI adapter would be 0x5000. Interrupt levels are assigned as level triggered. What this means is the interrupt is sharable as opposed to being edge triggered where the interrupts are not sharable. Two PCI devices should be able to share the same interrupt leaving more interrupts for other devices in the system that can not share interrupts. Interrupt values are assigned to other buses in the system, i.e., ISA EISA, just as in other non PCI systems. DMA is assigned differently to PCI devices than in other systems, leaving all conventional DMA channels available to other system devices. The following section is a review of the standard PnP architecture and how PCI is integrated into this model.

 

PCI and EMM386.EXE problem

There is a problem with using older versions of EMM386.EXE in a PCI system. In addition to performing memory management to help get around the DOS 1 Megabyte limitation, EMM386.EXE provides functionality to allow memory management to work with DMA devices. EMM386 has two functions, one of those being transparent re-programming of the host system’s DMA controller and VDS function calls (Virtual DMA Services). EMM386 will intercept and modify I/O instructions from programs that are unaware that a memory manager is present. The version of EMM386.EXE up to DOS 6.22 intercepted and modified I/O instructions in a way that interferes with PCI operation. A common problem resulting from this is adapter diagnostics failing or the machine hanging after the LAN driver is loaded.

 

Configuration and Troubleshooting

Configuration is normally handled through the systems BIOS and OS. The PCI Card should be able to be configured by the PnP BIOS without any problems, but we all know that will never be 100% reliable. In cases where the PnP BIOS fails to properly configure the PCI device, it's resources can be allocated through the System’s Configuration programs (firmware & Software). In EISA/PCI systems the first card in the system will be placed on the 16th slot (10 hex). The resources for the card can also be changed (IRQ and I/O)

*** Quick note: PCI cards can be configured to use edge or level interrupts (non-shared or shared), however the standard is for the adapter to be configured using level (shared) interrupt. Third party DMA is prohibited. Neither the PCI host controller nor any devices on the PCI bus use standard DMA Channels. PCI uses full 32 bit decode of I/O read and write addresses, meaning PCI devices can decode from 0 - 0FFFFFFFFh. ISA can only decode 12 bit addresses leaving an I/O base of 0 - 03ffh.

 

QStart and the KNE40BT PCI Ethernet Adapter

The QStart program that ships with the KNE40 family of adapters is slightly different then the previous revisions of this program. After the QStart program is executed there are four functions that are checked before presenting the first screen. The first is the presence of a Kingston KNE40 PCI Ethernet Adapter. The MAC address is checked to ensure that a Kingston Network Adapter is present in the system. The second function it performs is a search for multiple KNE40 adapters.  If QStart finds more than one adapter it allows the user to perform diagnostics or install drivers for each individual adapter. The third function is to retrieve the resources assigned by the PCI BIOS so QStart can display them to the installer. The fourth function is to check for an EMM386 driver and ensure that it is a correct version as described previously. If an acceptable version of EMM386 is not found the installer will be presented with a message detailing the problem and a solution. When all of these conditions are found to be satisfactory the installer will be presented with the initial QStart screen (see Fig 3).

 

Figure 3

The QStart program gives the installer the option to automatically run an ODI install. If the Automatic ODI installation is chosen, the QStart program will present the resources assigned by the system to the adapter by the PCI BIOS. It then runs adapter diagnostics (see fig 4). These will determine that the assigned resources are actually non conflicting. It will test internal registers as well as communicating with the host system.

Figure 4

If all these tests pass the installer will be presented with the final screen (see fig 5). This screen will provide the installer with a choice of four options depending on the NetWare server and if VLMs or NETX will be used. The other two boxes are for user input to setup the login name and preferred server. By clicking on the radio buttons the installer can select as many frame types needed for this installation. The information screen will display instructions on what is to be done to finish the installation. At any time during the installation the user can press function key "F1" and get context sensitive help about any part of the program. Next the installer clicks on continue. The information box will display all actions and changes that QStart will make to the system. The QStart program will create a \NWCLIENT subdirectory on the active hard drive; copy all drivers, VLMs and supporting files to that directory and create a NET.CFG and STARTNET.CFG files. During the copying of files to the \NWCLIENT directory, if an existing file is found, QStart will prompt the installer to either copy over that file, copy over all files or stop the process. This function is used anytime a file of the same name is found when QStart copies a file. After this is finished, the user will be prompted to either "Reboot" or previous. By choosing reboot, the system will be rebooted and the changes will become effective on the next system startup. If the installer needs to install another network operating system other than NetWare client software the Automatic features are still available. The installer would select "GENERIC" Install from the Automatic install section. After this button is clicked the adapter diagnostics screen appears, once again running Interrupt, register and systems communications check.

Figure 5

After the adapter diagnostics are completed the user is presented with a slightly different screen for diver install (Figure 6). Most of the other operating systems require that the driver be installed from within that particular operating system. This menu allows the installer to choose the drivers needed by highlighting the driver in the Operating systems lists box. After the driver is highlighted all the supporting files that will be copied are displayed in the files to be copied box. Note that every operating system contains an INSTALL.DOC document. This text file will give the user complete information on how to install the driver under the chosen operating system. The installer can also choose the directory and drive location to copy the files. This is extremely useful if the installer needs to copy all files to a floppy disk or the files are needed to be copied directly to a directory such as \BANYAN for Banyan Vines client Installation. After all choices are made, simply clicking on the copy button will copy all the drivers and supporting files will be copied to the destination directory. Other options on this screen are "View Doc," were the user can view the installation instructions for the Operating System or view the Driver revision for each driver on the disk. From the viewer the document can be printed out or viewed on the screen. The install.doc is a text file that will take a user through the installation of the driver under the chosen operating system, in some instances down to key strokes. In some cases for example, supporting files are included if any manual modifications must be made. The other options, "previous" will return the user to the previous screen. "Help" will bring context sensitive help and "cancel" will cancel that operation.

Figure 6

The Final selection from the main menu is custom. From this screen the installer can run basic adapter diagnostics. This is the same diagnostics that are run in the Automatic installations checking the Registers, Interrupt value and communicating with the system. The second option allows the installer to run a two node test. This consists of checking the cable between the two machines and verifying the lower layers of the OSI model. This test is extremely useful for ensuring proper communication between two nodes and verifying that the cabling is not a problem when diagnosing a problem. This test can be run between any two KNE40 PCI Ethernet Adapters or any other Kingston Ethernet Adapter that is configured using the QStart program. The third option is for the installer two install the adapter’s device drivers for an Operating System. This screen is the same one as shown in the Automatic Generic Installation. The last screen will allow the user to display an installation document for any of the supported operating systems.
