Generating Cryptographic Keys

The following table shows the functions that an application uses to generate cryptographic keys.

Function
Description
CryptDeriveKey Generates a key derived from a password.
CryptGenKey Generates a random key.

Although applications can create unlimited session keys, these keys are not preserved by the CSP from session to session. To preserve a key, export the key out of the CSP and import it into a key BLOB in the application’s memory space. For information on exporting and importing a key, see Exchanging Cryptographic Keys.

Session keys are created using either CryptGenKey or CryptDeriveKey. When a session key is generated, you must specify the algorithm to use for any subsequent encryption and decryption operations. This algorithm must be one of the symmetric algorithms supported by the CSP being used.

Because public-key algorithms are slow, it is impractical to use them to encrypt a large amount of data. In practice, symmetric algorithms are used for encryption and decryption, while public-key algorithms are used only to encrypt session keys.

For each user, the CSP usually maintains two public and private key pairs: the key exchange key pair, and the digital signature key pair. These keys are maintained from session to session.

There are a number of reasons for having two separate key pairs. For example, some CSPs use one algorithm for key exchange and another for digital signatures. Also, if some data, such as a session key, is both signed and encrypted with the same public key pair, subtle weaknesses can be introduced that make the data vulnerable.

The exchange key and the signature key pairs are created by calling the CryptGenKey function and specifying either AT_KEYEXCHANGE or AT_SIGNATURE. The CSP implements these keys in an application-independent manner. Applications are not permitted to know the details about the algorithm used.
