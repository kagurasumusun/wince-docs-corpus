Transitioning Between Power States

The following list describes the transitions between the power states for Windows CE–based target devices.

  • Power-on reset

    Power-on reset occurs when the target device is in the no power state and batteries are installed or AC power is applied for the first time. Power is applied to the CPU, ROM, and RAM, allowing the system to operate. When power is applied to the target device, RAM is cleared (both the file system and working RAM), the file system is initialized to its default state (copying initial files from ROM), and the target platform transitions to the on power state.

  • Cold boot

    A cold boot is a complete reset of the target device in which all applications are forcibly closed and working RAM and the file system are cleared. Typically, a cold boot is initiated by removing all power from the target device, including any backup batteries. When power is reapplied, the device performs a power-on reset.

  • Warm boot

    A warm boot — a transition from the on, idle, or suspend power state — closes all applications, clears working RAM, and preserves the file system. A warm boot can occur as a result of a software interrupt or by pressing the reset switch on the target device.

    An application can perform a warm boot of the device by calling the KernelIoControl function and passing the control code IOCTL_HAL_REBOOT. This I/O control code is an OEM-supplied routine, and may not be implemented on all devices.

  • On-to-idle

    When transitioning from the on power state to the idle power state, the CPU internal clock is stopped. The transition requires approximately 10 microseconds. While in the idle power state, the CPU uses little power and waits for an interrupt to occur. The kernel calls the OEMIdle function when there are no threads ready to run.

  • Idle-to-on

    Typically, the timer interrupt causes the CPU to transition from the idle power state to the on power state; however, any interrupt occurring on the target device can cause the transition. When the kernel receives an interrupt, the CPU is returned to full-power operation.

  • On-to-suspend

    The transition from the on power state to the suspend power state occurs during the following events:

    • Timeout of the user input inactivity timer.
    • The OFF switch on the target device is pressed.
    • An application program calls the GwesPowerOff function.
  • Suspend-to-on

    The transition from the suspend power state to the on power state occurs during the following events:

    • The on switch is pressed on the target device.
    • An alarm event.
    • A wake-up event — for example, carrier detection — on the target device, or an OEM-specific wake-up source, such as the ring indicator on a PCMCIA modem.
  • Critical-to-off

    A critical-to-off transition occurs when battery voltages for the primary batteries decrease to a critically low level that prevents the target device from performing a safe shutdown.

    Instead of executing an on-to-suspend transition, during which power is shut down in a timely manner, the critical-to-off transition bypasses the normal steps of turning off power to any peripherals or devices by immediately shutting down power to them and applying refresh voltage to the RAM. This preserves the file system and sets the CPU to the suspend power state.

    Recovery from a critical-to-off transition occurs when adequate power is applied to the device. Note that the process of a target device recovering from a critical-to-off transition is equivalent to a warm boot transition.

Outside of the OAL, the device drivers are also notified of on-to-suspend and suspend-to-on transitions.

During an on-to-suspend transition, the device driver can respond to these notifications by saving the current state of the hardware in RAM, and then shutting down the hardware in the appropriate order. Then, as the suspend-to-on transition occurs, the device driver can re-initialize the hardware and reset any necessary power states. For more information about power management routines, see the driver development documentation.

Because the drivers are called while the operating system is not scheduling other tasks, this limits the actions that a device driver can take in these power states. During the transitions, most function calls are not available and no other threads are running.

For example, a driver cannot enter a critical section to guard access to its resources in its power down and power up functions. However, these functions will run to completion without interruption because they are called in the kernel's power-up/power-down thread context. To allow more complex power-on scenarios, the SetInterruptEvent function is available during the PowerHandler state, and is used to signal the interrupt event for the driver. Typically, the PowerOn routine will set a driver variable indicating that PowerOn has occurred, and then call SetInterruptEvent. Once PowerOn has completed, the IST, which is scheduled as a result of the event, can use the driver variable to perform any complex power-on handling.
